# Browser Notes · 방향과 레퍼런스

조사일: 2026-10-23. 이름은 Browser Notes로 확정했다. 선언문은 수정 가능한 제안이다.

## 이 사이트의 역할

브라우저 기능을 소개하는 글 모음에서 한 단계 나아가, 질문을 선택하고 실험을 설계하고 판단을 수정하는 과정을 보여준다. 프레임워크는 연구 대상을 살펴보는 사례이며, 사이트의 대분류가 아니다. Next.js로 구현했다는 사실 자체가 포트폴리오의 주장이 되지는 않는다.

사용법을 설명하는 글도 의미가 있다. 다만 이 공간의 차별점은 **왜 이 질문을 골랐는가 → 무엇을 비교했는가 → 무엇 때문에 판단이 바뀌었는가**를 독자가 따라갈 수 있다는 데 둔다.

위 내용은 각 사이트에서 관찰한 특징과 이 프로젝트를 위한 해석을 구분한 것이다. 이미지, 코드, 브랜드 자산은 복제하지 않았다. Ink & Switch와 Maggie Appleton은 실제 화면도 확인했다.

## 정보 구조

- `/`: 철학 → 조작 가능한 개념 모델 → 현재 질문 → 노트 → 작성 원칙.
- `/notes`: 주제별 탐구 목록. 처음에는 목록 하나와 필터로 충분하다.
- `/notes/[slug]`: 질문 → 검증 계획 → 판단 기준 → 출처와 AI 협업 기록.
- `/lab`: 본문과 연결되는 실험. 현재는 Early Hints 개념 모델 한 개.
- `/about`: 작성자의 지향점. 현재 문구는 사용자 검토 전 제안.
- `/design-system`: 실제 토큰을 사용하는 색·타입·간격·상태 샘플.

### 카테고리는 필요하지만, 최소한으로

1. **로딩과 네트워크**: 언제 무엇을 가져오는가? HTTP, 캐시, 리소스 힌트.
2. **렌더링과 인터랙션**: 어떤 과정으로 보이고 반응하는가? 레이아웃, 전환, 입력, 접근성.
3. **웹의 경계**: 브라우저가 어디까지 책임져야 하는가? 플랫폼 제안, 개인정보, 자원 비용.

Chrome·Next.js·React·Early Hints 등은 태그로 남긴다. 여러 글에서 반복되는 새로운 질문이 생길 때만 주제를 늘린다. ‘웹의 경계’가 잡동사니 분류가 되면 질문 기준을 다시 좁힌다.

**주제**는 독자가 찾는 축이고 **상태**는 글의 진행 정도다. `질문 / 실험 설계 / 정리됨`으로 시작한다. `정리됨`도 검증 보증이나 영구적인 결론은 아니다. 개념 데모, 실제 측정, 개인 해석은 본문에서 구별한다.

## 비주얼 방향

따뜻한 종이색과 어두운 잉크색, 작은 주황색 강조를 사용한다. 영문 세리프는 선언과 타이틀에, 한글 산세리프는 읽는 내용에, 모노스페이스는 수치와 주석에 쓴다. 레이아웃은 넓은 여백, 가는 구분선, 번호, 여백의 메모로 연구 노트의 인상을 만든다.

히어로는 영상 대신 **질문 자체를 보여주는 조작 가능한 타임라인**으로 시작한다. 이 사이트에서 원하는 읽기 방식을 첫 화면에서 경험할 수 있고 외부 미디어 다운로드도 필요 없다. 향후 영상은 실제 실험 화면이나 관찰 대상을 보여줄 때 추가한다. 자동 재생 장식은 기본값으로 삼지 않는다.

## AI와 글을 쓰는 순서

1. 작성자: 질문, 문제를 겪은 맥락, 처음 예상한 답을 직접 적는다.
2. AI: 관련 명세와 구현 후보를 찾고, 비교 가능한 데모의 초안을 만든다.
3. 작성자: 출처를 읽고 반례를 정하며, 실험 조건을 확정한다.
4. AI + 작성자: 결과를 재현하고 원본 증거를 보관한다.
5. 작성자: 무엇을 믿게 됐는지, 무엇이 미해결인지, 자신의 선택 기준을 쓴다.
6. AI: 구조와 표현을 다듬되, 관찰하지 않은 결과나 설계자의 의도를 보충하지 않는다.

실제 기록에서는 브라우저·프레임워크·실행 환경의 버전과 확인 날짜를 남긴다. 개발자의 의도는 이슈·설계 문서 등 직접 근거가 없으면 추정으로 표시한다.

## Early Hints 첫 글의 핵심

“Next.js는 왜 Link 헤더만 주는가”를 전제로 확정하지 않는다. 먼저 최종 응답의 Link와 중간 103의 Link를 구분한다. 프레임워크가 생성한 리소스 정보, 런타임이 쓸 수 있는 응답 API, CDN이 실제로 내보낸 응답을 각각 관찰한다.

- [RFC 8297](https://www.rfc-editor.org/rfc/rfc8297): 103의 의미와 최종 응답과의 관계.
- [Chrome Early Hints](https://developer.chrome.com/docs/web-platform/early-hints): 서버 대기 시간을 사용하는 배경과 제약.
- [Cloudflare Early Hints](https://developers.cloudflare.com/cache/advanced-configuration/early-hints/): CDN이 힌트를 캐시하고 전송하는 사례.
- [Next.js headers](https://nextjs.org/docs/app/api-reference/config/next-config-js/headers): 사용자 지정 응답 헤더의 공식 인터페이스. 이 문서만으로 Next.js의 전체 103 지원 여부나 설계 의도를 결론 낼 수는 없다.

현재 데모는 실제 네트워크 요청, 103 전송 또는 성능 벤치마크가 아니다. 코드상의 `400ms`는 측정 결과가 아니라 모델의 가정이다.
