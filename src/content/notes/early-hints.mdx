## HTML을 이미 스트리밍하고 있다면, Early Hints는 어떤 기다림을 더 줄일 수 있을까?

HTML을 준비된 부분부터 보내는 상황에서도, 200 응답을 시작하기 전의 대기 시간은 남을 수 있다. 그 시간에 CSS 힌트를 먼저 받으면 어떤 차이가 생길까?

### 이 질문을 시작한 계기

Early Hints를 보면서, 서버가 HTML을 만드는 동안 브라우저는 무엇을 할 수 있는지 궁금해졌다. 그런데 Next.js가 HTML을 스트리밍한다면, 이미 리소스를 일찍 알려줄 수 있는 것 아닐까? 200 응답의 Link 헤더와 그보다 먼저 보내는 103 응답이 각각 언제 도착하는지 확인하고 싶었다.

### 처음 세운 가설

같은 스트리밍 구현이라도 200 응답 시작까지 기다리는 시간이 길고 필요한 CSS를 미리 알 수 있다면, 103으로 CSS 로딩을 앞당길 수 있을 것이라고 예상한다. 반대로 필요한 힌트를 담은 200 응답이 이미 빨리 도착한다면 추가 이점은 작을 것 같다. CSS 요청이 빨라진 정도가 화면 표시 시간의 개선과 같지는 않을 것 같다.

필요한 리소스를 알아내는 역할과 103 응답을 실제로 전송하는 역할은 서로 다른 곳에 있을 수 있다고 예상한다. 따라서 Next.js 코드뿐 아니라 실행 서버와 CDN의 동작도 확인해야 할 것 같다.

## 같은 Link 헤더인데, 도착 시점이 다르다

`Link`는 리소스 관계를 표현하는 헤더이고, `103`은 최종 응답 전에 보낼 수 있는 정보성 상태 코드입니다. 최종 응답에 Link 헤더가 있다는 사실만으로 103이 전송됐다고 판단할 수는 없습니다. [RFC 8297 ↗](https://www.rfc-editor.org/rfc/rfc8297)

### HTML 응답 시작과 완료는 다르다

브라우저가 HTML 전체를 수신하기 전에 받은 부분부터 파싱할 수 있는 것은 Next.js만의 기능이 아니다. 하지만 서버가 HTML 전체를 만든 뒤 전송하는지, 만드는 도중부터 준비된 부분을 전송하는지는 별개의 선택이다. 전송 중 데이터가 나뉘어 도착한다고 해서 서버도 HTML을 생성하는 도중에 보내고 있다고 판단할 수는 없다.

이 글에서 스트리밍 렌더링은 서버가 HTML 전체를 완성하기 전에 준비된 부분부터 전송하는 방식을 뜻한다. 이는 Next.js 밖에서도 가능하며, 모든 서버가 자동으로 그렇게 동작하는 것은 아니다. 어느 방식이든 200 응답 시작이 곧 HTML 수신 완료를 뜻하지 않는다. [React 스트리밍 설명 ↗](https://react.dev/reference/react-dom/server/renderToPipeableStream)

### 무엇을 비교할까?

원리는 특정 프레임워크에 한정되지 않는다. 여기서는 구체적인 실험 대상으로 Next.js를 선택하고, 준비된 HTML부터 전송하는 구현을 두 비교군에 동일하게 적용한다.

| 비교군 | HTML 응답 방식 | CSS 힌트 |
| --- | --- | --- |
| 기준 | 동일한 Next.js 스트리밍 구현 | 200 응답의 Link 헤더 |
| 실험 | 동일한 Next.js 스트리밍 구현 | 같은 힌트를 103으로 먼저 전달, 200 응답도 유지 |

1. 브라우저에서 실제로 103과 200 응답을 각각 받는가? Next.js·런타임·CDN 중 어디에서 힌트를 생성하고 전송하는가?
2. 103 유무만 바꿨을 때 CSS 발견·요청 시작과 LCP는 각각 얼마나 달라지는가?
3. 두 비교군에 같은 조건을 적용하면서, 200 응답이 일찍 시작하는 경우와 늦게 시작하는 경우를 비교하면 차이가 어떻게 바뀌는가?
4. 잘못 예측한 리소스나 캐시가 있는 경우에는 다운로드 비용과 이점이 어떻게 달라지는가?

스트리밍 OFF와 103 ON을 한 번에 비교하지 않는다. 같은 페이지·리소스·스트리밍 경계·데이터 대기·네트워크·캐시 조건을 유지하고 103 유무만 바꾼다. 실제로는 103이 네트워크 경쟁 등을 바꿀 수 있으므로 200 응답 시작과 HTML 수신 완료도 함께 기록한다.

### 실험 환경과 비교 조건

먼저 1번 질문을 확인했다. 브라우저가 103과 200을 각각 받는지, 그리고 Next.js·런타임·CDN 중 어디에서 힌트를 만들고 보내는지?

| 항목 | 조건 |
| --- | --- |
| 브라우저 | Chrome 155. Chrome DevTools Protocol로 기록 |
| 프레임워크 | Next.js 16.4.2, React 19.3.1. production 빌드 |
| 런타임 | Node.js 22.14.0 `http` 커스텀 서버. 103은 `res.writeEarlyHints()`로 전송 |
| CDN 역할 | Node.js `http2`로 만든 로컬 프록시(HTTP/2, TLS). 실제 CDN이 아니라 103을 전달·차단·생성하는 세 가지 동작만 흉내 냄 |
| 네트워크·캐시 | 로컬 조건은 모두 127.0.0.1. 측정마다 새 브라우저 컨텍스트를 열어 캐시와 연결이 비어 있는 상태에서 시작 |

서버가 HTML을 준비하는 동안의 대기를 만들기 위해, 요청마다 렌더링하면서 첫 화면을 1초 늦게 그리는 실험용 페이지(`/dynamic?delay=1000`)를 만들었다. 비교를 위해 빌드할 때 미리 렌더링해 두는 정적 페이지(`/static`)도 함께 두었고, 두 페이지 모두 같은 CSS 파일 하나를 쓴다.

103에 담을 CSS 경로는 커스텀 서버가 시작할 때, Next.js가 빌드하면서 남긴 경로별 CSS 목록에서 미리 읽어 두었다. React가 렌더링하면서 알려주는 Link는 첫 화면을 그린 뒤에야 나오기 때문에, 200보다 먼저 보내야 하는 103에는 쓸 수 없다.

| 조건 | 런타임 | 프록시 | 페이지 |
| --- | --- | --- | --- |
| ① 103 중계 | 103 보냄 | 103 전달 | 동적 |
| ② 103 버림 | 103 보냄 | 103 버림 | 동적 |
| ③ 프록시 학습 | 103 안 보냄 (Next.js만 응답) | 이전 200의 Link를 기억했다가 103 생성 | 동적 |
| ④ 정적 페이지 | 103 보냄 | 103 전달 | 정적 |
| ⑤ HTTP/1.1 직접 | 103 보냄 | 거치지 않음 | 동적 |

조건마다 5번씩 측정했다. 브라우저 쪽에서는 Chrome이 103을 Early Hints로 처리했는지(`Network.responseReceivedEarlyHints`), 103과 200의 도착 시각(`firstInterimResponseStart`, `finalResponseHeadersStart`), CSS 응답이 103에서 왔는지(`fromEarlyHints`)를 기록했다. 프록시 쪽에서는 요청 도착, 103, 200 헤더, 응답 완료 시각을 남겼다.

103으로 미리 받은 CSS는 브라우저가 캐시에서 꺼내 쓰기 때문에, 브라우저 기록에는 CSS를 네트워크에서 실제로 받은 시각이 남지 않는다. 그래서 CSS 요청 시각은 프록시 로그로 확인했다.

<div className="small-copy">

- `Network.responseReceivedEarlyHints`: Chrome이 103을 Early Hints로 받아들였을 때 DevTools에 보내는 이벤트다. DevTools 화면에서는 문서 요청의 Headers 탭에 Early hints headers로 나타난다. [Chrome DevTools Protocol ↗](https://chromedevtools.github.io/devtools-protocol/tot/Network/#event-responseReceivedEarlyHints)
- `firstInterimResponseStart`: 페이지 이동을 시작한 뒤 첫 중간 응답(1xx, 여기서는 103)의 첫 바이트가 도착한 시각이다. 중간 응답이 없으면 0이다. [MDN ↗](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming/firstInterimResponseStart)
- `finalResponseHeadersStart`: 최종 응답(200)의 헤더가 도착하기 시작한 시각이다. 두 시각 모두 Console에서 `performance.getEntriesByType("navigation")[0]`으로 볼 수 있다. [MDN ↗](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming/finalResponseHeadersStart)
- `fromEarlyHints`: 응답이 103 때 미리 받아 둔 것에서 나왔는지를 나타내는 값이다. DevTools 화면에서는 Initiator `Early-hints`, Size `(disk cache)`로 보인다. [Chrome DevTools Protocol ↗](https://chromedevtools.github.io/devtools-protocol/tot/Network/#type-Response) · [Chrome Early Hints ↗](https://developer.chrome.com/docs/web-platform/early-hints)

#### 2~4번 질문의 추가 조건

2~4번 질문은 같은 런타임·프록시·Chrome으로 측정하되, 103의 효과가 화면 표시까지 이어지는지 보기 위해 조건을 바꿨다. 103은 모두 프록시를 거쳐 HTTP/2로 전달했다.

| 항목 | 조건 |
| --- | --- |
| 느린 네트워크 흉내 | 프록시가 CSS를 초당 322 KB로만 내보내게 했다. CSS 파일(약 129 KB)을 혼자 받으면 약 400 ms가 걸리고, CSS 두 개를 동시에 받으면 대역폭을 나눠 쓴다. HTML과 JS는 제한하지 않았다 |
| 페이지 | 첫 화면을 그리기 전에 서버가 기다리는 페이지(대기 0·100·300·600·1,000 ms)와, 첫 화면은 바로 보내고 본문만 1,000 ms 뒤에 스트리밍하는 페이지 |
| 103에 담는 내용 | 없음(OFF), 쓰는 CSS(ON), 쓰지 않는 CSS만(틀린 힌트), 쓰지 않는 CSS와 쓰는 CSS 함께(둘 다) |
| 캐시 | 기본은 매번 빈 캐시. 캐시 조건에서는 같은 페이지를 한 번 열어 CSS를 캐시에 넣은 뒤 다시 측정 |
| 반복 | 조건마다 10번 |

같은 컴퓨터 안에서는 CSS가 몇 ms 만에 받아져서 화면 표시 차이가 드러나지 않기 때문에 대역폭을 제한했다. 400 ms는 앞의 개념 모델이 가정한 CSS 수신 기간과 같은 값이다. 실제 네트워크의 왕복 지연이나 HTTP/2 우선순위, JS와의 경쟁은 반영하지 않은 단순한 흉내다.

LCP(Largest Contentful Paint)는 페이지에서 가장 큰 콘텐츠가 화면에 그려진 시각으로, 브라우저의 `largest-contentful-paint` 기록에서 읽었다. 실험 페이지의 LCP는 제목(`h1`)이고, CSS가 도착해야 그려진다.

<p className="small-copy">103 사용은 Chrome이 103을 Early Hints로 처리한 횟수이고, 103에 Link는 그중 Link가 담겨 있던 횟수다. 103 도착은 처리 여부와 관계없이 103이 도착한 시각이다. 도착 시각은 브라우저의 Navigation Timing 기준 중앙값이다. ③의 4/5는 2~5회째 요청이다. 아래 curl 기록의 시각은 ms까지만 남겼다.</p>

#### 1. Next.js만으로는 103이 없었다

커스텀 서버의 103을 끄고 Next.js만 응답하게 하면, 동적 페이지는 200에만 Link가 있었고 정적 페이지는 Link도 없었다. 이 Link는 React가 렌더링하면서 모은 CSS를 Next.js가 200 응답 헤더에 붙인 것이다. 헤더는 200 응답과 한 묶음으로 나가므로, 서버가 첫 화면을 준비하는 1초 동안은 보낼 수 없고 200과 같은 순간에 도착했다.

```
# 동적 페이지
14:34:18.458 > GET /dynamic?delay=1000 HTTP/1.1
14:34:19.480 < HTTP/1.1 200 OK
14:34:19.480 < Link: </_next/static/chunks/11jpq2l3uwkyz.css>; rel=preload; as="style"

# 정적 페이지
14:39:31.241 > GET /static HTTP/1.1
14:39:31.244 < HTTP/1.1 200 OK
```

Next.js 팀은 완전히 정적인 페이지에는 Link 헤더의 시간 이득이 없어 production에서는 넣지 않는다고 설명했다(PPR를 켜면 넣는다). [GitHub 토론 ↗](https://github.com/vercel/next.js/discussions/76995) 정적 페이지는 빌드할 때 HTML을 미리 만들어 두기 때문에 응답 헤더 바로 뒤에 HTML이 따라오고, CSS를 가리키는 `<link>` 태그도 HTML 맨 앞에 있다. 헤더로 한 번 더 알려 줘도 CSS를 발견하는 시점이 거의 같아서 그런 것 같다.

#### 2. 런타임이 보낸 103은 HTTP/2로 전달될 때만 Chrome이 사용했다

런타임이 Next.js에 요청을 넘기기 전에 103을 쓰면, 103이 200보다 약 1초 먼저 도착했다. 103의 Link(`as=style`)는 커스텀 서버가 쓴 값이고, 200의 Link(`as="style"`)는 React가 쓴 값이다. 같은 CSS를 가리키지만 만든 곳이 다르다.

```
14:33:53.851 > GET /dynamic?delay=1000 HTTP/2
14:33:53.853 < HTTP/2 103
14:33:53.853 < link: </_next/static/chunks/11jpq2l3uwkyz.css>; rel=preload; as=style
14:33:54.861 < HTTP/2 200
14:33:54.861 < link: </_next/static/chunks/11jpq2l3uwkyz.css>; rel=preload; as="style"
```

Chrome은 ①에서 5번 모두 103을 받았고, 103 때 받아 둔 CSS를 재사용했다. DevTools에서는 이 CSS의 Initiator가 `Early-hints`, Size가 `(disk cache)`로 보인다. 문서의 Headers 탭에는 200의 Response headers와 별도로 Early hints headers가 나온다.

반면 프록시 없이 HTTP/1.1로 연결한 ⑤에서는, 103이 1~2 ms에 도착한 기록(`firstInterimResponseStart`)은 남았지만 Chrome은 이를 Early Hints로 처리하지 않았다. CSS는 200을 받은 뒤에야 요청했다. Chrome이 HTTP/1.1의 103을 사용하지 않는다는 문서 내용과 같다.

#### 3. 103을 받으면 CSS 다운로드가 200보다 먼저 끝났다

<EarlyHintsMeasurement />

프록시 로그로 보면 ①에서는 문서 요청 후 3.4 ms에 CSS 요청이 들어와 6.8 ms에 다 보냈고, 200 헤더는 1,008 ms에 나갔다. ②에서는 CSS 요청이 200 이후인 1,010.6 ms에 들어왔다.

DevTools 화면만 보면 ①의 CSS는 약 1.03초에 0 ms로 처리된 것처럼 보인다. 이는 문서가 캐시에서 CSS를 꺼내 쓴 시점이다. 네트워크에서 실제로 받은 시점은 프록시 로그에서만 확인됐다.

같은 컴퓨터 안의 측정이라 CSS 전송은 몇 ms 만에 끝났다. 앞당긴 시간이 실제 화면 표시로 얼마나 이어지는지는 2번 질문에서 확인한다.

#### 4. 중간 계층이 103을 버리면 브라우저에는 흔적이 남지 않았다

②에서 런타임은 매번 103을 보냈고 프록시 로그에도 `103 dropped`가 남았다. 하지만 브라우저에는 103 수신 기록이 없었고, CSS는 200을 받은 뒤 일반 요청으로 받았다. 브라우저 기록만으로는 "103을 보내지 않았다"와 "중간에 버려졌다"를 구분할 수 없다.

  <img src="/notes/early-hints/devtools-drop.png" alt="Chrome DevTools Network 패널. 11jpq2l3uwkyz.css의 Initiator가 Other, Size가 0.3 kB, 시간이 6 ms다." width="1640" height="768" />
  <figcaption>② 103 버림. CSS의 Initiator가 Other이고 Size에 실제 전송량(0.3 kB)이 나온다. 200의 Link 헤더로 시작한 요청으로 보인다.</figcaption>
</figure>

#### 5. 프록시가 200의 Link를 기억하면, Next.js만으로도 두 번째 요청부터 103이 생겼다

③에서 런타임은 103을 보내지 않았다. 1회째에는 103이 없었고, 프록시가 그 200의 Link를 기억한 뒤인 2~5회째에는 프록시가 직접 103을 보냈다. 이때 103의 Link는 `as="style"`로, React가 200에 쓴 값을 그대로 옮긴 것이다. 무엇을 알려줄지는 Next.js가, 언제 보낼지는 프록시가 정한 셈이다.

이 프록시는 Cloudflare 문서에 설명된 동작을 흉내 낸 것이고, 실제 Cloudflare로는 확인하지 않았다. 또 이 방식은 200에 Link가 있어야 동작하므로, Link가 없는 정적 페이지에는 기억할 정보가 없다.

#### 6. 정적 페이지에서는 103과 200 사이가 거의 없었다

④에서 103은 2 ms, 200은 5 ms에 도착했다(프록시 기준으로는 103이 0.8 ms, 200이 2.6 ms). 서버가 기다릴 일이 없으니 103이 먼저 갈 여유도 거의 없다.

#### 참고: 배포된 이 페이지(Vercel)

통제된 비교는 아니지만 배포된 이 노트 페이지도 확인했다. Vercel은 HTTP/2로 응답하며 103을 보냈지만, 103에는 `server`와 `x-vercel-id`만 있고 Link가 없어 미리 받은 리소스는 없었다. curl로는 `Sec-Fetch-Mode: navigate`를 붙였을 때만 103이 보였으므로, 브라우저와 같은 헤더 없이 확인하면 103이 없다고 잘못 판단할 수 있다.

#### 1번 질문에 대한 답

- **브라우저가 받는가**: 103이 HTTP/2로 끝까지 전달되면 Chrome은 103과 200을 각각 받았고, 103의 Link로 CSS를 미리 받았다. HTTP/1.1이거나 중간 계층이 버리면 사용하지 않았다.
- **어디서 만들고 보내는가**: 이 실험에서 Next.js는 103을 보내지 않았다. 103에 담을 내용은 Next.js의 빌드 결과나 200의 Link에서 나왔고, 실제로 보낸 곳은 런타임(커스텀 서버)이나 CDN 역할의 프록시였다.

결국 같은 페이지라도 어느 계층에서 관찰하느냐에 따라 "103이 있다"는 답이 달라졌다. 최종 응답의 Link만 보고 103 전송 여부를 판단할 수 없다는 처음의 전제를 실제로 확인했다.

**답**: 103만 켜도 CSS 요청은 서버 대기만큼(약 1초) 앞당겨졌지만, LCP는 CSS 수신 시간만큼(408 ms) 줄었다.

### 3번 질문: 서버 대기 시간에 따라 차이는 어떻게 바뀌나

같은 조건에서 첫 화면 전 대기 시간만 바꿨다. 마지막 줄은 첫 화면을 바로 보내고 본문만 1,000 ms 뒤에 스트리밍한 페이지다.

- 대기가 CSS 수신 시간보다 짧으면(0~300 ms) 대기 시간만큼 줄었다. 이때 103 ON의 LCP는 대기와 상관없이 약 430~440 ms로, CSS 수신이 끝나는 시점에 맞춰졌다.
- 대기가 CSS 수신 시간보다 길면(600, 1,000 ms) 약 400 ms에서 더 늘지 않았다. 이때 103 ON의 LCP는 HTML이 도착하는 시점에 맞춰졌다.
- 첫 화면을 바로 보내는 스트리밍 페이지에서는 차이가 없었다. 200과 `<link>`가 6 ms에 도착해 103 없이도 CSS를 거의 바로 요청했고, LCP는 1,000 ms 뒤에 오는 본문이 결정했다.

**답**: 줄어드는 시간은 "서버가 첫 화면 전에 기다린 시간"과 "CSS를 받는 시간" 중 짧은 쪽이었다. 첫 화면을 바로 보내는 스트리밍에서는 줄일 시간이 없었다.

## 실험 후, 내 판단은 어떻게 바뀌었나?

처음 세운 가설은 방향이 대부분 맞았다. 다만 실험을 하고 나서 "얼마나 줄어드는지"와 "어디서 보내야 하는지"가 훨씬 구체적으로 바뀌었다.

- **200을 오래 기다릴수록 103이 CSS를 앞당긴다**: 맞았다. 다만 LCP가 줄어드는 데에는 한계가 있었다. 줄어든 시간은 첫 화면 전 서버 대기와 CSS를 받는 시간 중 짧은 쪽이었고, 대기를 1,000 ms로 늘려도 약 400 ms에서 멈췄다.
- **200이 이미 빨리 오면 이점이 작다**: 맞았다. 대기가 없는 페이지는 LCP가 8 ms만 줄었고, 정적 페이지는 103과 200이 3 ms 차이로 도착했으며, 첫 화면을 바로 보내는 스트리밍 페이지는 LCP 차이가 없었다. 여기서 생각이 바뀐 부분이 있다. 처음에는 "HTML을 스트리밍하고 있느냐"를 기준으로 생각했는데, 실제로 중요한 건 **첫 화면이 언제 나가느냐**였다. 같은 Next.js 스트리밍 구현이라도 `Suspense` 밖에서 데이터를 기다리면 첫 화면과 200이 그만큼 늦고, 103은 바로 그 기다림만 줄일 수 있었다.
- **CSS 요청이 빨라진 만큼 화면이 빨라지지는 않는다**: 맞았다. CSS 요청은 약 1,011 ms 앞당겨졌지만 LCP는 408 ms 줄었다. HTML이 오기 전에는 그릴 내용이 없기 때문이다.
- **리소스를 아는 곳과 103을 보내는 곳이 다를 것이다**: 생각보다 더 분명하게 나뉘어 있었다. Next.js는 103을 보내지 않았고, 200의 Link도 첫 화면을 그린 뒤에야 생겨서 103에 쓰기에는 늦었다. 103은 빌드 결과를 읽은 런타임이나 CDN이 보내야 했고, 중간 계층이 103을 버리면 브라우저 기록만으로는 알 수 없었다.

예상하지 못한 것도 있었다. 틀린 힌트는 다운로드 낭비로 끝나지 않고, 서버 대기가 짧을 때는 진짜 CSS와 대역폭을 나눠 써서 103이 없을 때보다 화면을 늦췄다. Chrome이 HTTP/1.1로 온 103을 쓰지 않는다는 점, Vercel이 Link 없는 103을 보낸다는 점도 실험 전에는 생각하지 못했다.

그래서 제목의 질문에는 이렇게 답할 수 있을 것 같다. HTML을 이미 스트리밍하고 있다면, Early Hints가 더 줄일 수 있는 기다림은 **첫 화면이 나가기 전의 서버 대기**뿐이다. 첫 화면을 이미 빨리 보내고 있다면 줄일 것이 거의 없다.

### 어떤 조건에서 사용하고, 사용하지 않을까?

103은 아래 세 가지가 모두 맞을 때 쓸 만하다고 본다.

1. **첫 화면 전에 서버가 기다리는 시간이 있다.** 인증 확인, `Suspense`로 나누기 어려운 데이터, 멀리 있는 원 서버처럼 200을 늦추는 원인이 있어야 한다. 이득은 그 대기와 CSS 수신 시간 중 짧은 쪽을 넘지 않는다.
2. **그 대기 전에 필요한 리소스를 확실히 안다.** 빌드 결과에서 읽은 경로별 CSS처럼 요청마다 바뀌지 않는 것만 힌트로 보낸다. 틀린 힌트는 손해가 될 수 있다.
3. **103이 브라우저까지 HTTP/2 이상으로 전달된다.** 런타임이 보내고 중간 계층이 전달하는지, CDN이 직접 만드는지 계층마다 확인해야 한다.

반대로 이런 경우에는 쓰지 않을 것 같다.

- **정적 페이지나 캐시된 HTML**: 200이 바로 오므로 앞당길 시간이 없다.
- **기다림을 `Suspense`나 `loading.js`로 나눌 수 있는 경우**: 첫 화면을 먼저 보내면 CSS도 그때 바로 발견된다. 103을 붙이기 전에 첫 화면을 빨리 보내는 쪽을 먼저 고칠 것이다.
- **힌트가 틀릴 가능성이 있는 경우**: 배포마다 바뀌는 파일 이름을 예전 응답에서 배워 보내거나, 요청마다 필요한 리소스가 달라지는 경우다.
- **재방문이 대부분이라 CSS가 캐시에 있는 경우**: 103이 와도 미리 받을 것이 없다. 손해는 없지만 이득도 없다.

Next.js 프로젝트라면 한 가지를 더 따져야 한다. Next.js가 103을 직접 보내지 않으므로, 쓰려면 커스텀 서버나 CDN 설정이 필요하다. Vercel에서는 앱 코드로 103을 보낼 방법을 찾지 못했다. 그 운영 비용에 비해 줄일 수 있는 시간이 CSS 수신 시간 정도라면, 대부분은 `Suspense`로 첫 화면을 먼저 보내는 쪽이 더 단순한 선택이라고 본다.
