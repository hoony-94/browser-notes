## 먼저 결과부터

탭 10개에서 각각 롱폴링을 시작하자, HTTP/1.1에서는 여섯 탭의 요청만 서버에 도착했다. 나머지는 빈 소켓을 기다렸다. 기다리던 탭은 특정 대화방의 이벤트를 27초 뒤에 받았지만, 모든 탭에 보내는 이벤트는 14 ms 안에 받았다. 같은 연결 제한에 걸려도 이벤트를 보내는 방식에 따라 지연이 달라졌다.

HTTP/2에서는 이런 소켓 대기 없이 열 탭이 모두 연결됐다. 대표 탭이나 SharedWorker로 연결을 공유한 경우에도 대화방 이벤트는 모두 7 ms 안에 도착했다. 다만 대표 탭이 멈췄을 때 연결을 복구하거나, 서버가 여러 대화방의 접속 상태를 함께 관리하도록 바꾸는 일이 필요했다. 연결 수를 줄이는 것만으로 끝나는 문제는 아니었다.

## 탭을 여러 개 열어 둔 사용자에게, 서버 연결은 하나면 충분할까?

- 탭마다 롱폴링(또는 SSE, WebSocket) 연결을 열면, 서버와 브라우저에서 무슨 일이 생길까?
- 브라우저의 호스트별 연결 수 제한에 걸리면, 기다리는 탭은 무엇을 놓칠까? 같은 호스트의 일반 API도 같이 느려질까?
- 한 탭만 서버와 연결하고 받은 이벤트를 나머지 탭에 전달할 수 있을까? 그 탭을 닫거나 브라우저가 그 탭을 멈추면 어떻게 될까?
- 연결 하나가 "이 탭이 지금 어느 대화방을 보고 있는지"까지 서버에 알리는 역할을 겸한다면, 연결을 합쳐도 그 정보를 유지할 수 있을까?
- 여러 탭이 동시에 로그인 토큰을 갱신하면 어떻게 될까?
- 숨겨진 탭의 연결과 타이머는 계속 살아 있을까?

### 이런 궁금증이 생긴 이유

업무용 서비스 사용자는 메일, 결재, 메신저처럼 여러 화면을 탭으로 띄워 두고 하루 종일 쓴다. 내가 맡은 서비스도 탭마다 공통 헤더에서 롱폴링으로 알림을 받는다. 서버는 요청을 최대 30초 동안 유지하다가 응답하고, 탭은 응답을 받으면 곧바로 다음 요청을 보낸다.

이 요청에는 "이 탭이 지금 보고 있는 것"도 파라미터로 보낸다. 서버는 이 값을 바탕으로 탭의 접속 상태를 관리한다. 메신저라면 지금 열어 둔 대화방이 그 값이다. 이 글에서는 편의상 "대화방"이라고 부르지만, 게시판이나 문서도 같은 방식으로 생각할 수 있다. 알림 서버와 일반 API 서버는 호스트가 다르고, 둘 다 아직 HTTP/1.1이다.

HTTP/1.1에서는 브라우저가 한 호스트에 여는 연결이 최대 6개이고, 여러 탭이 이 한도를 나눠 쓴다고 알고 있었다. 그렇다면 일곱 번째 탭의 롱폴링은 서버에 도착하기도 전에 기다려야 한다. 그동안 알림을 받지 못하고, 서버에서도 그 탭이 어느 대화방을 보고 있는지 알 수 없지 않을까? 같은 호스트로 가는 일반 API 요청도 밀릴 것 같았다.

오류가 뜨는 대신 알림만 늦어진다면 원인을 알아채기 어려울 것 같아서, 실제로 그런지부터 확인하고 싶었다. 여러 탭이 연결 하나를 나눠 쓰면 어떨까 하는 생각도 들었다.

### 처음 세운 가설

- 탭마다 연결하면 연결 수는 탭 수와 같다. HTTP/1.1에서는 일곱 번째 탭부터 브라우저 안에서 기다리고, 기다리는 탭에 가는 이벤트는 그 탭만을 위한 것이든 모든 탭에 가는 것이든 최대 30초(롱폴링 대기 시간) 늦을 것이다. 같은 호스트의 일반 API는 여섯 번째 탭부터 밀릴 것이다. HTTP/2면 이 제한이 없을 것이다.
- Web Locks로 대표 탭을 하나 정하고, 그 탭이 받은 이벤트를 BroadcastChannel로 전달하면 연결은 1개로 줄어든다. 다만 서버가 연결을 기준으로 대화방 접속 상태를 관리하므로, 하나의 연결에 여러 대화방을 등록할 수 있도록 바꿔야 한다. 서버를 바꾸지 않으려면 같은 대화방을 보는 탭끼리 대표를 두어야 한다. 이때 연결 수는 서로 다른 대화방 수에 일반 알림용 연결 하나를 더한 값이 된다.
- 대표 탭이 숨겨지면 다른 탭도 이벤트를 늦게 받을 것이다. 브라우저가 대표 탭을 동결하면(freeze) 잠금이 유지된 채 실행이 멈춰, 다른 탭도 이벤트를 받지 못할 것이다. 대표 탭을 닫으면 잠금이 해제돼 다음 탭이 대표 역할을 넘겨받을 것이다.
- SharedWorker가 가장 단순할 것이다. 탭이 하나라도 남아 있으면 워커가 계속 실행되므로, 어느 탭이 닫혀도 다른 탭이 연결을 넘겨받을 필요가 없을 것이다. 다만 2026년에야 Baseline이 됐으니 오래된 브라우저를 위한 대안은 필요하다.
- 토큰 갱신도 Web Locks로 한 번에 한 탭만 하게 하면 경쟁이 사라질 것이다.
- 숨겨진 탭의 롱폴링은 계속 돌지만, 5분 넘게 숨겨지면 타이머가 1분에 한 번으로 제한되어 타이머에 기대는 재시작 로직은 늦어질 것이다.

## 실험 환경

실제 서비스의 코드는 쓰지 않고, 같은 동작을 하는 서버와 페이지를 Node.js로 만들었다.

| 항목 | 조건 |
| --- | --- |
| 브라우저 | Chrome 156.0.8078.48, macOS 15. |
| 서버 | 같은 포트에 호스트 이름 셋. 페이지(`app.localhost`), 알림 롱폴링(`lp.localhost`), 일반 API(`api.localhost`). 브라우저의 소켓 풀은 스킴·호스트·포트로 나뉘므로 실제 서비스처럼 알림과 API가 다른 풀을 쓴다. 같은 코드를 자체 서명 TLS 위의 HTTP/2(`lp2.localhost`)로도 띄웠다 |
| 롱폴링 | 요청을 최대 30초 동안 유지하되, 이벤트가 있으면 바로 응답한다. 요청의 `since` 이후 이벤트는 다시 보내 준다. 요청에 실린 대화방 이름을 그 연결의 접속 상태로 기록한다. 페이지는 응답을 받자마자 다음 요청을 보낸다(XHR, 타임아웃 120초) |
| 탭 | 10개. 탭 1~3은 대시보드(보고 있는 대화방 없음), 탭 4·8은 대화방 A, 5·9는 대화방 B, 6·10은 대화방 C, 7은 대화방 D |
| 이벤트 | 새 메시지처럼 대화방 A(또는 D)를 보는 탭에만 보내는 이벤트와, 전체 알림처럼 모든 탭에 보내는 이벤트. 두 종류를 차례로 발행하고, 서버가 이벤트를 만든 시점부터 탭이 받을 때까지 걸린 시간을 잰다 |
| 알림 | 탭이 이벤트를 화면에 띄우는 대신 서버에 "띄웠다"고 보고해 횟수를 센다 |
| 동결·폐기 | `chrome://discards`에서 `Freeze`로 동결하고, 해당 탭을 다시 선택해 실행을 재개했다. 폐기 실험에는 같은 페이지의 `Urgent Discard`를 사용했다 |
| 반복 | 기본적으로 시나리오마다 1회 측정했다. 대표 탭 시나리오는 구현을 고치며 4회 실행했고, 본문에는 마지막 실행의 수치를 적었다. 여러 번 측정한 항목은 따로 표시했다 |

동결은 탭의 실행을 일시적으로 멈추는 것이고, 폐기는 메모리에서 페이지를 내리는 것이다. 탭을 다시 선택하면 동결된 탭은 실행을 이어가고, 폐기된 탭은 페이지를 새로 불러온다.

실험에 사용한 Chrome 156에서는 `chrome://chrome-urls`의 "내부 디버깅 페이지 사용"을 켜야 `chrome://discards`에 접근할 수 있었다. 동결할 때는 다른 탭을 선택해 대상 탭을 숨김 상태로 뒀다.

## 1. 탭마다 연결하면

### 서버에는 여섯 개만 닿았다

탭 10개가 각자 롱폴링을 시작했지만, 서버에서 확인한 동시 연결은 6개였다. Chromium은 HTTP/1.1에서 스킴·호스트·포트가 같은 그룹에 소켓을 6개까지만 연다(`g_max_sockets_per_group`). 나머지 네 탭의 요청은 브라우저 안에서 빈 소켓을 기다리다가, 먼저 보낸 요청이 30초 뒤에 끝나면 서버로 전송된다.

새로 전송된 요청도 최대 30초 동안 소켓을 사용한다. 응답을 받은 탭은 곧바로 다음 요청을 보내지만, 이 요청은 다시 대기열 끝에 들어간다. 그래서 나중에 연 네 탭만 기다리는 게 아니라 열 탭이 돌아가며 기다린다. 3분 동안 측정했을 때 먼저 연 탭은 측정 시간의 33%, 나중에 연 탭은 49% 동안 서버에 연결되지 못했다.

서버가 연결을 기준으로 어느 대화방에 접속해 있는지 판단한다면, 연결이 없는 동안에는 접속 상태도 유지되지 않는다. 서버 기록에서도 각 탭의 연결이 30~33초씩 끊겼다가 다시 열리는 것을 확인했다.

### 한 대화방에만 가는 이벤트는 27초 늦고, 모두에게 가는 이벤트는 늦지 않았다

| 이벤트 | 받은 탭 | 지연 |
| --- | --- | --- |
| 대화방 A 이벤트 | 탭 4 (연결돼 있던 탭) | 2 ms |
| 대화방 A 이벤트 | 탭 8 (기다리던 탭) | 27,205 ms |
| 대화방 D 이벤트 | 탭 7 | 3 ms |
| 모든 탭 이벤트 | 탭 10개 | 4~14 ms |

대기 중인 탭은 요청이 서버에 도착해야 대화방 이벤트를 받을 수 있다. 이번 실험에서 탭 8은 다른 탭의 롱폴링 대기 시간 30초가 끝나 소켓이 빌 때까지 기다렸다.

모든 탭에 보내는 이벤트는 달랐다. 서버가 대기 중이던 여섯 요청에 한꺼번에 응답하면서 소켓 여섯 개가 동시에 비었다. 기다리던 네 탭의 요청도 바로 전송됐고, 서버는 `since` 이후의 이벤트를 다시 보내 줬다. 그래서 처음 예상과 달리 이 이벤트는 지연이 크지 않았다.

<MultiTabEventDiagram />

이 차이는 서버가 이벤트를 어느 연결에 보내느냐에 달려 있어서, 실제 서비스에서는 서버 쪽 규칙을 확인해야 한다.

### 같은 호스트의 일반 요청은 여섯 번째 탭부터 막혔다

<MultiTabWaitChart />

탭 6개에서는 각 탭의 롱폴링이 정상적으로 동작했다. 하지만 소켓 6개를 모두 사용하고 있어서, 같은 호스트로 보낸 fetch 요청 한 건은 28초를 기다렸다. 탭 5개까지는 2 ms였다. 호스트가 다른 일반 API는 탭 10개에서도 2 ms였다.

지금 서비스는 알림과 일반 API의 호스트가 분리돼 있어 이 영향을 피할 수 있다. 다만 알림 호스트에 일반 API를 추가하면 그 요청도 롱폴링과 소켓을 나눠 써야 한다.

### HTTP/2에서는 소켓을 기다리지 않았다

같은 페이지를 HTTP/2 서버에 연결하자 열 탭의 롱폴링 요청이 모두 서버에 도착했다. TCP 연결 하나에서 스트림 10개를 사용하는 방식이었다. 대화방 이벤트는 4 ms, 모든 탭 이벤트는 2~12 ms에 도착했고, 같은 호스트의 일반 요청도 1 ms 만에 응답을 받았다. 모든 탭이 측정 시간 내내 연결을 유지했다. 이번 실험에서는 HTTP/1.1의 소켓 6개 제한으로 생겼던 대기가 나타나지 않았다.

## 2. 대표 탭이 연결하고 BroadcastChannel로 나눠 주면

### 대표 탭 하나: 연결 1개, 대신 서버가 대화방 목록을 받아야 했다

탭마다 `navigator.locks.request("lp-leader", …)`를 호출해 두면 잠금을 획득한 탭 하나가 대표가 된다. 대표 탭은 BroadcastChannel로 각 탭이 보고 있는 대화방을 확인한 뒤, 대화방 목록(A·B·C·D)을 담아 롱폴링 요청 하나를 보낸다. 서버에서 받은 이벤트는 BroadcastChannel로 다른 탭에 전달한다.

| 항목 | 결과 |
| --- | --- |
| 서버 연결 | 1개 |
| 대화방 이벤트 지연 | 1~4 ms (탭 4·8·7) |
| 모든 탭 이벤트 지연 | 2~6 ms |
| 같은 호스트의 일반 요청 | 3 ms |
| 알림 | 이벤트마다 1번. 알림용 잠금을 따로 두어 한 탭만 띄우게 했다 |
| 대표 탭을 닫으면 | 다음 탭이 잠금을 받기까지 109~124 ms, 그 탭의 첫 요청이 서버에 닿기까지 207~211 ms(대화방 목록을 모으는 200 ms 포함). 그 뒤 이벤트 2~3 ms |

이 방식을 쓰려면 서버가 하나의 연결에 여러 대화방을 등록할 수 있어야 한다. 지금 서버는 연결 하나에 대화방 하나만 등록하므로 프로토콜을 바꿔야 한다.

### 대표 탭이 멈추자 다른 탭도 이벤트를 받지 못했다

<MultiTabDelayChart />

`chrome://discards`에서 대표 탭을 동결하자 다른 아홉 탭도 대화방 이벤트를 받지 못했다. 대표 탭이 잠금을 유지한 채 서버 응답을 처리하지 못했기 때문이다. 대표 탭을 다시 선택해 실행을 재개한 뒤에야 다른 탭으로 이벤트가 전달됐다. 이벤트가 도착하기까지 24.1초가 걸렸고, 같은 탭이 대표 역할을 이어갔다. 자동으로 복구된 것이 아니라, 동결을 직접 해제할 때까지 기다린 결과다.

한 가지 구분할 점이 있다. 이 실험에서는 버튼을 눌러 강제로 동결했다. 당시 대표 탭의 Is Freezable은 ✘였고, 이유 중 하나는 "holding Web Lock"이었다. 잠금을 보유하고 있어 자동 동결 대상에서는 제외된 상태였다.

따라서 이 결과를 Chrome이 평소에도 대표 탭을 자동으로 멈춘다는 뜻으로 받아들이면 안 된다. 여기서 확인한 것은 대표 탭의 실행이 멈추면 다른 탭의 이벤트 수신도 함께 중단된다는 점이다.

이를 복구하기 위해 대표 탭이 응답하는지 확인하는 처리를 추가했다. 대표 탭은 1초마다 BroadcastChannel로 생존 신호(heartbeat)를 보낸다. 다른 탭은 무작위로 정한 4~5.5초 동안 신호가 오지 않으면 `{ steal: true }`로 잠금을 가져와 새 대표가 된다.

이렇게 바꾸자 대표 탭을 동결한 뒤 발행한 대화방 이벤트가 3.7초 만에 도착했다. 여러 번 측정했을 때는 3.7~4.0초였다. 기존 대표 탭은 실행이 재개된 뒤 잠금 요청이 거부된 것을 확인하고 대표 역할을 중단했다. 서버 연결도 다시 1개로 줄었다.

이 구현에서 두 번 실수했다. 먼저, 대표 탭이 대화방 목록을 모으는 200 ms 사이에 잠금을 빼앗겨도 롱폴링 요청을 시작하는 문제가 있었다. 이미 대표가 아닌 탭의 요청이 남아 연결이 6개까지 늘었다. 또 대표가 되자마자 다른 탭에서 "나 여기 있어"라는 메시지가 오면 롱폴링을 재시작하면서 한 탭이 연결을 2개 열었다.

세대 번호를 확인해 이전 대표의 요청이 뒤늦게 시작되지 않도록 막고, 새 요청을 보내기 전에 이전 요청을 반드시 중단하도록 고쳤다. 대표 탭 방식에서는 역할이 바뀌는 동안 이런 경합이 생길 수 있어 직접 처리해야 했다.

### 대화방마다 대표 탭: 연결은 대화방 수 + 1, 서버는 그대로

이번에는 대화방마다 대표 탭을 하나씩 뒀다. 대화방 A는 `lp:A`, 일반 알림은 `lp:general`처럼 잠금 이름을 구분하면, 같은 대화방을 보는 탭 중 하나만 서버에 연결한다. 대화방을 보지 않는 대시보드 탭들은 일반 알림용 연결 하나를 나눠 쓴다. 연결 하나에 대화방 하나를 등록하는 기존 서버의 규칙을 그대로 쓸 수 있다.

| 항목 | 결과 |
| --- | --- |
| 서버 연결 | 5개 (대화방 A·B·C·D + 일반 알림) |
| 대화방 이벤트 지연 | 1~2 ms |
| 모든 탭 이벤트 지연 | 2~3 ms |
| 대화방 A의 대표를 닫으면 | 같은 대화방을 보던 탭이 잠금을 받기까지 7~11 ms, 첫 요청 207 ms, 그 뒤 이벤트 2 ms |
| 일반 알림 대표가 멈추면 | 다른 아홉 탭은 모든 탭 이벤트를 4~6 ms에 받았다. 대화방 대표들도 같은 이벤트를 받아 BroadcastChannel로 다른 탭에 전달하기 때문이다 |

이 구성에서 연결 수는 "서로 다른 대화방 수 + 일반 알림용 연결 1개"다. 같은 대화방을 보는 탭이 많을수록 연결을 줄일 수 있지만, 서로 다른 대화방 8개와 일반 알림용 연결을 열면 9개가 되어 다시 6개 제한에 걸린다. 그래도 대화방 대표 하나가 멈췄을 때 그 대화방의 이벤트만 영향을 받는다는 점은 대표를 하나만 두는 방식보다 나았다.

</section>

## 3. SharedWorker가 연결하면

각 탭은 포트를 통해 워커와 통신한다. 워커는 각 탭이 보고 있는 대화방 목록을 모아 롱폴링 요청 하나를 보내고, 서버에서 받은 이벤트를 모든 포트로 전달한다.

| 항목 | 결과 |
| --- | --- |
| 서버 연결 | 1개 (대화방 목록 A·B·C·D) |
| 대화방 이벤트 지연 | 1~7 ms |
| 모든 탭 이벤트 지연 | 1~13 ms |
| 알림 | 이벤트마다 1번 |
| 워커를 처음 만든 탭을 닫으면 | 연결이 그대로 유지됐고 새 연결은 없었다. 이벤트 3~6 ms |
| 탭을 하나씩 닫으면 | 대화방 목록도 줄어들어, 남아 있는 탭이 보는 대화방만 유지됐다(마지막엔 대화방 C 하나) |
| 마지막 탭을 닫으면 | 3.5초 안에 서버 연결이 끊겼다. 탭을 다시 열자 연결 1개가 새로 생겼다 |

워커가 연결을 유지하므로 탭 사이에서 대표 역할을 넘겨받을 필요가 없다. 덕분에 대표가 바뀌는 과정에서 생겼던 경합도 피할 수 있었다.

대신 이 구현에서는 탭이 닫혔다는 사실을 워커에 직접 알려야 했다. 탭이 `pagehide`에서 종료 메시지를 보내면 워커가 해당 대화방을 목록에서 뺀다. 탭이 비정상 종료돼 메시지를 보내지 못하면 그 대화방은 목록에 남는다.

이 방식도 서버가 하나의 연결에 여러 대화방을 등록할 수 있어야 한다. 서버를 바꾸기 어렵다면 워커에서 대화방마다 별도의 연결을 열도록 구현할 수 있다.

</section>

## 4. 잠금으로 토큰 갱신 충돌을 대부분 막았지만, 한 번은 실패했다

갱신 토큰을 한 번 사용하면 새 토큰을 발급하는 서버를 만들었다. 토큰 만료 시간은 5초, 갱신 응답 시간은 300 ms로 설정했다. 열 탭이 만료 1.5초 전부터 250 ms마다 갱신을 시도하게 하고, 20초 동안 성공과 실패 횟수를 셌다.

| 방식 | 시도 | 성공 | 실패 |
| --- | --- | --- | --- |
| 탭마다 따로 | 65 | 5 | 60 (탭마다 5~7번) |
| Web Locks로 한 탭씩 | 6 | 5 | 1 |

잠금이 없으면 갱신 응답을 기다리는 300 ms 사이에 다른 탭들도 같은 토큰으로 갱신을 요청했다. 이미 사용된 토큰이라 대부분 실패했다. 갱신 실패 시 로그아웃하도록 처리하는 서비스라면 이 때문에 사용자가 로그아웃될 수 있다.

잠금을 사용한 경우에는 잠금을 획득한 탭이 localStorage를 다시 읽도록 했다. 다른 탭이 이미 토큰을 갱신했다면 추가로 요청하지 않고 넘어간다.

남은 한 번의 실패는 다른 탭이 localStorage에 저장한 새 토큰을 아직 읽지 못해서였다. Chrome의 localStorage는 프로세스마다 캐시를 두고 비동기로 동기화하므로, 잠금을 획득한 직후에도 몇 ms 동안 이전 값이 읽힐 수 있다. 갱신한 탭이 BroadcastChannel로 새 토큰을 전달하거나, 401 응답을 받으면 저장된 토큰을 다시 읽고 한 번 더 시도하는 처리가 필요하다.

이 결과는 토큰을 localStorage에 저장한 구현에서 나온 것이다. 쿠키로 인증하는 서비스는 토큰을 읽고 갱신하는 방식이 다르므로 같은 결과가 나온다고 단정할 수 없다. 다만 쿠키를 사용해도 여러 탭이 동시에 갱신을 요청할 수는 있다. 쿠키 갱신 응답이 겹칠 때의 충돌은 [쿠키 표준에서도 설명한다](https://www.rfc-editor.org/rfc/rfc6265.html#section-4.1.1). 저장 위치와 별개로 동시 갱신을 어떻게 처리할지 정해야 한다.

갱신 응답이 1 ms였던 첫 실행에서는 잠금 없이도 실패가 없었다. 응답 시간을 300 ms로 늘리자, 한 탭이 응답을 기다리는 사이에 다른 탭도 갱신을 요청하면서 충돌이 드러났다.

</section>

## 5. 숨긴 탭과 멈춘 탭

### 숨긴 탭에서도 롱폴링은 유지됐지만, 타이머 실행 횟수는 줄었다

탭 두 개를 열고, 하나는 선택하지 않은 상태로 6분 30초 동안 뒀다. 타이머 제한이 예상되는 5분 이후에도 동작을 확인하려고 시간을 넉넉히 잡았다. 1초 간격으로 설정한 `setInterval`은 0~4분에는 분당 60번 실행됐지만, 5분부터는 분당 1번으로 줄었다. Chrome의 강한 타이머 제한이 적용된 것이다.

그동안 롱폴링은 계속 연결돼 있었고, 1분·3분·5분 30초·6분 30초 시점에 보낸 이벤트도 2~7 ms에 도착했다. 응답 콜백에서 바로 다음 요청을 보내기 때문에 타이머 제한의 영향을 받지 않았다. 대표 탭을 숨겼을 때도 다른 탭은 이벤트를 5~10 ms에 받았다. 처음 예상과 달리 숨김 상태만으로 이벤트 수신이 늦어지지는 않았다.

다만 4초마다 `readyState`를 확인해 끊긴 롱폴링을 재시작하는 로직이라면 영향을 받는다. 같은 타이머 제한이 적용되면 복구 여부를 확인하는 주기도 1분으로 늘어나, 연결이 끊긴 뒤 복구까지 최대 1분이 걸릴 수 있다.

### 동결된 탭은 실행을 재개한 뒤에야 이벤트를 받았다

탭마다 연결하는 방식에서 대화방 A를 보는 탭 하나를 `chrome://discards`로 동결했다. 소켓 대기와 동결의 영향을 구분하기 위해 HTTP/2를 사용했다. 같은 대화방의 다른 탭은 이벤트를 2 ms에 받았지만, 동결된 탭은 다시 선택해 실행을 재개한 뒤에야 받았다. 이 탭의 수신 지연은 34초였다.

동결된 탭의 롱폴링은 서버의 대기 시간 30초가 지나면서 종료됐고, 다음 요청은 전송되지 않았다. 35초 뒤에는 서버에 그 탭의 연결이 남아 있지 않았다. 접속 상태를 연결로 판단하는 서버라면 이 탭은 대화방을 나간 것으로 처리된다. 대표 탭을 하나 두는 방식에서 그 대표가 동결되면, 2절에서 확인했듯 다른 탭도 이벤트를 받지 못한다.

</section>

## 실험 후, 내 판단은 어떻게 바뀌었나?

### 연결 수와 지연 비교

먼저 탭이 정상적으로 동작할 때의 결과를 모았다. 아래의 연결 수는 서버에서 동시에 처리한 롱폴링 수다. HTTP/2의 10개는 TCP 연결 10개가 아니라, TCP 연결 하나에 열린 스트림 10개를 뜻한다.

| 방식 | 동시 롱폴링 수 | 3분간 받은 요청 수 | 접속 상태 유지율 | 서버 변경 |
| --- | --- | --- | --- | --- |
| 탭마다 연결 · HTTP/1.1 | 6개 | 36건 | 51~67% | 불필요 |
| 탭마다 연결 · HTTP/2 | 10개 | 60건 | 100% | 불필요 |
| 대표 탭 하나 | 1개 | 6건 | 100% | 필요 |
| 대화방마다 대표 | 5개 | 30건 | 100% | 불필요 |
| SharedWorker | 1개 | 6건 | 100% | 필요 |

요청 수와 접속 상태 유지율은 3분 동안 한 번 측정했다. 접속 상태 유지율은 서버가 각 탭의 접속 상태를 유지한 시간의 비율이다. 앞의 탭별 그래프는 95초 동안 측정한 별도 결과라 수치가 다르다. 여기서 서버 변경은 한 연결에 여러 대화방을 등록하도록 프로토콜을 바꾸는 것을 뜻한다.

| 방식 | 대화방 이벤트 수신 지연 | 새 탭의 대화방 등록 시간 |
| --- | --- | --- |
| 탭마다 연결 · HTTP/1.1 | 연결 중인 탭 2 ms, 대기 중인 탭 27.2초 | 26.7~27.5초 |
| 탭마다 연결 · HTTP/2 | 4 ms | 6~8 ms |
| 대표 탭 하나 | 1~4 ms | 160~168 ms |
| 대화방마다 대표 | 1~2 ms | 217~227 ms |
| SharedWorker | 1~7 ms | 7~13 ms |

대화방 등록 시간은 새 탭을 연 뒤 서버에 해당 대화방의 접속 상태가 반영되기까지 걸린 시간이다. 세 번 측정한 최솟값과 최댓값을 적었다. 기존 이벤트를 빨리 받는 것과 새 탭의 대화방이 빨리 등록되는 것은 별개였다.

### 탭이 동결되거나 폐기됐을 때

동결 실험에서는 멈춘 탭이 다른 탭의 이벤트 수신에도 영향을 주는지 확인했다. 대표 탭을 쓰는 방식에서는 대표를 동결했다.

| 방식 | 다른 탭에 미친 영향 | 복구 결과 |
| --- | --- | --- |
| 탭마다 연결 · HTTP/1.1·HTTP/2 | 다른 탭은 계속 수신 | 동결된 탭만 실행 재개 후 수신 |
| 대표 탭 하나 | 모든 탭의 수신 중단 | 생존 신호로 대표를 교체하면 3.7~4.0초 뒤 수신 |
| 대화방마다 대표 | 같은 대화방의 수신만 중단 | 대표를 교체해 5.0초 만에 수신 재개 |
| SharedWorker | 다른 탭은 계속 수신 | 워커가 연결 유지 |

대표 교체 처리가 없으면 동결된 대표 탭의 실행이 재개될 때까지 기다려야 했다. 앞에서 측정한 24.1초도 직접 실행을 재개한 시점에 따라 나온 값이다.

폐기 실험에서는 탭을 메모리에서 내린 뒤 연결이 어떻게 바뀌는지 확인했다. 탭마다 연결하는 방식은 HTTP/2에서만 측정했다.

| 방식 | 탭을 폐기한 뒤의 동작 |
| --- | --- |
| 탭마다 연결 · HTTP/2 | 해당 탭의 연결만 끊겼다. 페이지를 다시 불러오면 연결도 복구됐다 |
| 대표 탭 하나 | 1.5초 안에 다른 탭이 대표가 됐다. 폐기 실험 중 보낸 이벤트의 수신 지연은 2 ms였다 |
| 대화방마다 대표 | 1.5초 안에 같은 대화방의 다른 탭이 대표가 됐다. 폐기 실험 중 보낸 이벤트의 수신 지연은 49 ms였다 |
| SharedWorker | 서버 연결은 유지됐다. 다만 워커에 폐기된 탭의 포트 기록이 남았다 |

SharedWorker 실험에서는 워커가 관리하는 포트 수가 10개에서 11개로 늘었다. 서버 연결이 유지돼도, 더 이상 쓰지 않는 포트 기록은 따로 정리해야 한다.

### 대표가 바뀌는 동안 이벤트를 놓치지는 않았나?

100 ms마다 이벤트를 보내면서 대표 탭을 닫거나 동결해 봤다. 대표를 하나만 두는 방식과 대화방마다 두는 방식 모두, 탭을 닫는 실험에서는 40건 중 0건, 동결하는 실험에서는 90건 중 0건이 누락됐다. SharedWorker도 워커를 처음 만든 탭을 닫았을 때 40건을 모두 전달했다.

수신이 잠시 늦어져도 이벤트가 누락되지는 않았다. 다만 이번 결과는 서버가 요청의 `since` 이후 이벤트를 다시 보내 주는 조건에서 나온 것이다.

### 가설과 실제 결과

실험 전의 가설과 결과를 비교하면 다음과 같다.

| 처음 세운 가설 | 관찰 |
| --- | --- |
| HTTP/1.1에서는 일곱 번째 탭부터 기다리고, 그 탭에 가는 이벤트는 어떤 것이든 최대 30초 늦는다 | 반만 맞았다. 특정 대화방의 이벤트는 27초 늦었지만, 모든 탭에 가는 이벤트는 14 ms 안에 왔다. 서버가 여러 요청에 동시에 응답하면서 소켓이 비었기 때문이다 |
| 같은 호스트의 일반 API는 여섯 번째 탭부터 밀린다 | 맞았다. 28~30초를 기다렸다. 호스트가 다르면 2 ms |
| HTTP/2면 소켓 6개 제한으로 기다리지 않는다 | 열 탭 모두 대기 없이 요청을 보냈다 |
| 대표 탭 하나로 연결을 1개로 줄일 수 있다. 서버는 대화방 목록을 받아야 한다 | 예상과 같았다. 대표 탭을 닫은 뒤 다음 대표가 요청을 보내기까지 약 0.2초가 걸렸다 |
| 대표 탭이 숨겨지면 모두 늦어지고, 멈추면 모두 멈춘다 | 숨김 상태에서도 6분 30초 동안 이벤트를 5~10 ms에 전달했다. 강제로 동결하자 다른 탭도 수신을 멈췄고, 대표 교체 처리를 넣으면 약 4초 만에 복구됐다 |
| 대화방마다 대표를 두면 연결은 대화방 수 + 1 | 대화방 4개와 일반 알림에 총 5개를 썼다. 일반 알림 대표가 멈춰도 다른 탭은 전체 이벤트를 받았다 |
| SharedWorker는 탭 사이에서 연결을 넘겨받을 필요가 없다 | 예상과 같았다. 대신 이 구현에서는 탭이 닫힐 때 워커에 직접 알려야 했다 |
| 토큰 갱신에 잠금을 쓰면 충돌이 사라진다 | 대부분 막았지만, localStorage의 새 값이 다른 탭에 늦게 반영돼 1번 실패했다. 쿠키 기반 인증은 별도로 확인해야 한다 |
| 숨긴 탭의 롱폴링은 유지되고 타이머는 5분 뒤 1분 1회가 된다 | 맞았다 |

### 지금 서비스에 적용한다면

1. **HTTP/1.1을 쓰는 동안에는 알림 호스트에 롱폴링만 둔다.** 실험에서는 탭 여섯 개부터 같은 호스트의 일반 요청이 최대 30초를 기다렸다. 지금처럼 일반 API와 호스트를 분리해서 운영한다는 원칙을 명시해 두려 한다.
2. **TLS 종단에서 HTTP/2를 켜는 것을 먼저 검토한다.** 브라우저와 연결되는 구간을 HTTP/2로 바꾸면, 뒷단은 HTTP/1.1로 유지해도 소켓 6개 제한에 따른 대기를 피할 수 있다. 이번에 확인한 지연 문제에는 이 변경이 가장 직접적인 해결책으로 보인다.
3. **HTTP/2를 적용하기 전에는 대화방마다 대표 탭을 두는 방식을 고려한다.** 서버를 바꾸지 않고 같은 대화방을 보는 탭들이 연결을 공유할 수 있다. 대화방을 옮길 때는 기존 잠금을 해제하고 새 대화방의 잠금을 요청해야 한다. 대표 탭의 생존 신호가 끊기면 `steal`로 대표를 교체하고, 새 요청을 보내기 전에는 이전 요청을 중단하도록 한다.
4. **서버가 하나의 연결에 여러 대화방을 등록할 수 있다면 SharedWorker를 쓰고 싶다.** 이번 구현에서는 대표 역할을 넘기는 처리가 없어 더 단순했다. 탭이 `pagehide`에서 종료 메시지를 보내도록 하고, SharedWorker를 지원하지 않는 브라우저에서는 탭마다 연결하는 방식을 쓴다.
5. **토큰 갱신에는 잠금을 쓰고, 새 토큰도 다른 탭에 전달한다.** 잠금을 획득한 뒤 갱신이 필요한지 확인하고, 갱신 결과는 BroadcastChannel로 알린다. 401 응답을 받으면 저장된 토큰을 다시 읽어 한 번 더 시도한 뒤 로그아웃 여부를 판단한다.
6. **끊긴 롱폴링의 복구를 타이머에만 맡기지 않는다.** 숨긴 탭에서는 복구를 확인하는 타이머도 분당 한 번으로 제한될 수 있다. 응답 콜백에서 바로 다음 요청을 보내고, `visibilitychange`로 탭이 다시 보이게 됐을 때 연결 상태를 한 번 더 확인한다.

### 아직 확인하지 못한 것

- Safari와 Firefox. HTTP/1.1 연결 제한은 둘 다 6개지만 소켓 풀의 순서와 SharedWorker 동작은 Chrome에서만 봤다.
- Service Worker가 연결을 유지할 수 있는지. 할 일이 없으면 브라우저가 실행을 중단하므로 어려울 것으로 보고 실험에서 제외했다.
