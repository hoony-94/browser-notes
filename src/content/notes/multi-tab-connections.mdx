## 탭을 여러 개 열어 둔 사용자에게, 서버 연결은 하나면 충분할까?

- 탭마다 WebSocket이나 SSE 연결을 열면, 서버와 브라우저에서 무슨 일이 생길까?
- 한 탭만 서버와 연결하고 나머지 탭에 나눠 줄 수 있을까? 그 탭을 닫거나 브라우저가 그 탭을 멈추면 어떻게 될까?
- 여러 탭이 동시에 로그인 토큰을 갱신하면 어떻게 될까?
- 숨겨진 탭의 연결과 타이머는 계속 살아 있을까?

### 이 질문을 시작한 계기

업무용 서비스 사용자는 메일, 결재, 메신저처럼 여러 화면을 탭으로 띄워 두고 하루 종일 쓴다. 실시간 알림을 위해 탭마다 연결을 열면, 서버 연결 수는 사용자 수에 탭 수를 곱한 만큼 늘어난다. 알림이 탭 수만큼 겹쳐 뜨거나, 탭이 많아지면 실시간 갱신이 멈추거나, 갑자기 로그아웃되는 증상도 이 구조에서 나올 수 있다. 연결은 브라우저마다 하나면 충분하지 않을까 궁금했다.

### 처음 세운 가설

- 탭마다 연결하면 연결 수는 탭 수와 같다. HTTP/1.1의 SSE는 6개에서 막히고, HTTP/2면 막히지 않을 것이다.
- Web Locks로 대표 탭 하나만 연결하고 BroadcastChannel로 나눠 주면 연결은 1개가 된다. 대신 대표 탭이 숨겨져 느려지거나 멈추면, 모든 탭이 같이 늦어질 것이다.
- SharedWorker가 가장 단순할 것이다. 다만 2026년에야 Baseline이 됐으니 오래된 기기는 따로 대비해야 한다.
- 토큰 갱신도 Web Locks로 한 번에 한 탭만 하게 하면 경쟁이 사라질 것이다.

## 탭마다 연결하면 생기는 일

| 문제 | 이유 |
| --- | --- |
| 연결 수 = 사용자 × 탭 | 서버 메모리와 로드밸런서 연결이 탭 수만큼 늘어난다 |
| HTTP/1.1의 SSE는 6개에서 막힘 | 브라우저는 HTTP/1.1에서 한 도메인에 연결을 6개까지만 연다. 탭 전체를 합친 수다. Chrome과 Firefox는 이를 고치지 않기로 했다(Won't fix). HTTP/2는 연결 하나에 스트림을 기본 100개까지 함께 쓴다 |
| 알림이 겹침 | 각 탭이 같은 메시지를 받아 각자 알림을 띄운다 |
| 토큰 갱신 경쟁 | 갱신 토큰을 한 번 쓰면 새 토큰으로 바뀌는 방식이면, 동시에 갱신한 탭 중 하나만 성공하고 나머지는 이미 쓴 토큰을 내민다 |
| 숨겨진 탭의 타이머 | Chrome은 5분 넘게 숨겨진 페이지의 연쇄 타이머를 1분에 한 번만 실행할 수 있다(조건 있음). 연결 확인(heartbeat)을 타이머로 보낸다면 늦어질 수 있다 |

Chrome의 강한 타이머 제한(intensive throttling)은 네 조건이 모두 맞을 때 걸린다. 페이지가 5분 넘게 숨겨져 있고, 타이머가 5번 이상 이어졌고, 30초 넘게 소리가 없고, WebRTC를 쓰지 않을 때다. WebSocket이 열려 있을 때 어떻게 되는지는 글에 나오지 않아 확인이 필요하다.

<section id="browser">

## 브라우저가 주는 탭 사이 협력 기능

| 기능 | 하는 일 | 지원 |
| --- | --- | --- |
| BroadcastChannel | 같은 출처의 탭끼리 메시지를 주고받는다 | Baseline |
| Web Locks API | 탭 사이에서 잠금을 건다. 대표 탭 뽑기, 한 번에 한 탭만 실행하기 | Baseline |
| SharedWorker | 같은 출처의 여러 탭이 워커 하나를 함께 쓴다 | Baseline 2026 (Newly available) |
| Service Worker | 탭과 따로 동작하지만, 할 일이 없으면 브라우저가 멈춘다. 연결을 오래 들고 있기 어려울 것으로 예상(확인 필요) | Baseline |
| `storage` 이벤트 | localStorage 변경을 다른 탭에 알린다. 예전 방식 | Baseline |

</section>

<section id="candidates">

## 비교해 볼 방법

| 방법 | 서버 연결 수 | 대표가 사라지면 | 확인할 것 |
| --- | --- | --- | --- |
| 탭마다 연결 | 탭 수 | 해당 없음 | 기준. HTTP/1.1 SSE에서 일곱 번째 탭 |
| 대표 탭(Web Locks) + BroadcastChannel | 1 | 다음 탭이 잠금을 넘겨받아 다시 연결 | 넘겨받는 데 걸리는 시간, 대표 탭이 숨겨졌을 때의 지연 |
| SharedWorker | 1 | 마지막 탭이 닫힐 때까지 유지 | 지원하지 않는 브라우저 대비, 디버깅 난이도 |

토큰 갱신은 따로 비교한다. 각 탭이 따로 갱신하는 경우와, Web Locks로 한 번에 한 탭만 갱신하고 결과를 나눠 주는 경우다.

Next.js 같은 프레임워크는 이 부분을 다루지 않는다. 브라우저 기능을 직접 쓰거나 라이브러리를 쓰게 되는데, 라이브러리들이 이 기능을 어떻게 감싸는지도 볼 예정이다.

</section>

<section id="plan">

## 실험 아이디어

- 연결 수를 세는 Node.js 서버를 만든다. WebSocket과 SSE, HTTP/1.1과 HTTP/2를 나눈다.
- CDP로 탭 10개를 연다. 위 세 방법마다 다음을 잰다.
  - 서버 연결 수
  - 메시지 하나가 모든 탭에 도착하는 시간
  - 대표 탭을 닫았을 때 다른 탭이 넘겨받기까지의 시간
  - 숨긴 탭과 멈춘 탭(CDP `Page.setWebLifecycleState`)에서의 지연
- 토큰 갱신: 토큰이 곧 만료되게 해 두고, 열 개 탭이 동시에 요청할 때 갱신 요청 수와 실패 수를 센다.
- 실제 Chrome 창에서 알림이 몇 번 뜨는지 화면으로 남긴다.
