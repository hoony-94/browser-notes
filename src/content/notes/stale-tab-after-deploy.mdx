## 먼저 결과부터

문제를 세 층으로 나눠 실험했다. 열려 있던 탭이 **깨지지 않게** 버티는 일, 새 버전이 나왔다는 것을 **알아채는** 일, 그리고 사용자가 덜 방해받는 순간에 **넘어가는** 일이다.

- **깨지지 않게**: 이전 빌드의 정적 파일을 남겨 두자 지연 로딩 오류가 사라졌다. 서버 응답 형식이 바뀐 화면은 이전 클라이언트를 이전 서버 코드로 보내야 했다. Next.js의 Server Action은 빌드마다 ID가 바뀌어 깨졌지만, 암호화 키를 고정하자 이전 탭에서도 그대로 동작했다.
- **알아채게**: 응답 헤더에 빌드를 실어 보내면 추가 요청 없이 다음 요청 때 알았다. 탭으로 돌아올 때 한 번 확인하면 오래 머문 탭도 잡혔다. 한 탭이 알면 BroadcastChannel로 1ms 만에 다른 탭에 전달됐다.
- **넘어가게**: 탭이 숨겨졌을 때 새로고침하면 사용자는 기다리지 않았다. 돌아오면 이미 v2였고, 작성 중인 글과 스크롤은 앱이 저장해 둔 만큼 남았다. Chrome에서는 v2를 미리 렌더링해 두면, 새로고침에 0.63초 걸리던 교체가 0.015초로 줄었다.

## 배포 직후 열려 있던 탭을, 사용자가 눈치채지 못하게 최신으로 바꿀 수 있을까?

- 배포 직후 열려 있던 탭에서는 정확히 무엇이 깨질까?
- 브라우저가 이미 주는 기능만으로 새 버전을 알아채고, 자연스러운 순간에 넘어갈 수 있을까?
- 프레임워크(Next.js)가 해 주는 것과 해 주지 않는 것은 무엇이고, 해 주지 않는 것은 어떻게 채울 수 있을까?

### 이 질문을 시작한 계기

실무에서 ChunkLoadError를 오류 메시지로 감지해, 대체 UI에서 새로 고침을 안내한 적이 있다. 동작은 했지만, 사용자는 무언가를 하려던 순간에 오류 화면을 보고 새로 고침을 눌러야 했다. 오류가 난 뒤에 수습하는 방식이다. 배포가 잦을수록 이런 순간도 잦아진다. 오류가 나기 전에, 사용자가 덜 방해받는 순간에 조용히 넘어가는 방법이 있는지 궁금했다.

### 처음 세운 가설

1. 지연 로딩 오류의 대부분은 새 배포가 이전 정적 파일을 지워서 생긴다. 이전 파일을 남기면 사라진다. 다만 서버 쪽 약속(API 응답 형식, Server Action)이 바뀌면 여전히 깨진다.
2. 이전 클라이언트를 이전 서버 코드로 보내는 버전 고정은 직접 운영하는 서버에서도 요청 헤더 하나로 만들 수 있다.
3. 새 버전 감지는 별도 폴링보다 응답 헤더가 싸다. 오래 머무는 탭은 탭으로 돌아올 때 한 번 확인하면 충분하다.
4. 가장 자연스러운 순간은 다음 이동, 탭이 숨겨졌을 때, 뒤로 가기로 돌아왔을 때다.
5. 새로 고침의 빈 화면은 v2를 미리 렌더링해 두면 없앨 수 있다(Chrome).

</section>

## 다른 분야에서 빌려온 생각

웹만의 문제는 아니다. 실행 중인 프로그램을 새 버전으로 바꾸는 일은 다른 분야에도 있고, 각자 굳어진 방식이 있다.

| 분야 | 하는 방식 | 웹으로 옮기면 |
| --- | --- | --- |
| 모바일 앱 | 보통은 "업데이트 권장", 호환이 깨지면 최소 지원 버전 아래를 "강제 업데이트" | 대부분의 배포는 자연스러운 순간에 넘기고, 호환이 깨지는 배포만 즉시 넘긴다 |
| 브라우저·데스크톱 앱 | 새 버전을 뒤에서 받아 두고, 다시 시작할 때 적용 | v2를 미리 받아 두거나(prerender), 탭이 숨겨졌을 때 바꾼다 |
| 서버 API | 하위 호환 변경. 필드는 먼저 추가하고, 지우는 것은 이전 클라이언트가 사라진 뒤에 | 이전 탭이 새 서버와 말이 통하게 한다 |
| 배포 플랫폼 | 블루그린 배포, 이전 클라이언트를 이전 서버로 보내는 버전 고정 | 이전 정적 파일 보존, 빌드 헤더로 이전 서버 코드에 연결 |
| 기능 플래그 | 배포와 공개를 분리 | 서둘러 넘겨야 하는 배포 자체를 줄인다 |

이 표에서 세 층을 얻었다. **깨지지 않게** 버티고, 새 버전을 **알아채고**, 적절한 순간에 **넘어간다**. 실험도 이 순서로 나눴다.

</section>

## 실험 환경

두 가지 앱을 만들었다. 브라우저 기능만 쓰는 앱으로 브라우저가 할 수 있는 일을 재고, Next.js 앱으로 프레임워크가 해 주는 일을 따로 확인했다.

| 항목 | 조건 |
| --- | --- |
| 브라우저 | Chrome 155.0.8059.85, macOS 15. 측정은 헤드리스, 화면은 실제 창 캡처 |
| 브라우저 기능만 쓰는 앱 | 목록·상세·글쓰기 화면, 지연 로딩 모달(`import()`), Navigation API 라우터. v1과 v2를 빌드. v2는 서버 응답 필드 이름을 바꿈(`items` → `rows`) |
| 배포 흉내 | 서버 하나가 언제든 v2로 바뀐다. 배포 방식은 세 가지: 덮어쓰기(이전 파일 삭제), 이전 파일 보존, 이전 파일 보존 + 버전 고정(요청의 `x-build-id`를 보고 그 빌드의 서버 코드가 응답) |
| 지연 | 서버가 HTML과 데이터를 각각 0.3초 늦게 보냄 |
| Next.js 앱 | Next.js 16.4.2. 같은 포트의 v1 서버를 v2로 교체(직접 운영 흉내). 링크, `router.refresh()`, 뒤로 가기, `next/dynamic` 모달, Server Action |
| 반복 | 시각을 재는 항목은 3~5회, 중앙값 |

미리 렌더링은 측정 방법을 바꿔야 했다. Chrome은 시작한 탭에 디버거(CDP)가 붙어 있으면 미리 렌더링을 하지 않았다(`PrerenderingDisabledByDevTools`). 그래서 이 항목만 탭에 붙지 않고, 페이지가 `sendBeacon`으로 서버에 시각을 보고하게 했다.

## 1. 깨지지 않게: 무엇이 깨지고, 무엇으로 막히나

v1 탭을 열어 둔 채 v2를 배포하고, 그 탭에서 모달을 열고 다른 화면으로 이동했다.

| 배포 방식 | 지연 로딩 모달 | 서버 응답 형식이 바뀐 화면 |
| --- | --- | --- |
| 덮어쓰기 | **실패**. `TypeError: Failed to fetch dynamically imported module` | **깨짐**. v1 코드가 v2 응답을 읽지 못함 |
| 이전 파일 보존 | v1 모달이 정상으로 열림 | **깨짐** |
| 이전 파일 보존 + 버전 고정 | v1 모달이 정상으로 열림 | 정상. v1 서버 코드가 응답 |

- 이전 파일을 남기는 것만으로 지연 로딩은 안전해졌다. 파일 이름에 내용의 해시가 붙어 있으니 v1과 v2 파일은 서로 덮어쓰지 않는다. Next.js 빌드 두 개를 비교해 보면 청크 11개 중 9개는 이름이 같았고, 바뀐 2개만 문제가 된다.
- 서버 응답 형식이 바뀌면 이전 파일만으로는 부족했다. 이전 클라이언트가 보낸 빌드 헤더를 보고 이전 서버 코드로 응답하자 정상이 됐다. 대가는 두 버전의 서버 코드를 함께 돌리는 것이다. 이게 어렵다면 응답 형식을 하위 호환으로만 바꿔야 한다.
- 오류의 이름은 만드는 쪽마다 달랐다. 브라우저 기본 ES 모듈은 `TypeError`, Next.js 16(Turbopack)은 이름이 `ChunkLoadError`이고 메시지가 `Failed to load chunk ...`다. webpack은 같은 이름에 메시지가 `Loading chunk ... failed`다. 메시지 문자열로 감지하면 번들러가 바뀔 때 놓친다.

</section>

## 2. 알아채게: 새 버전이 나왔다는 것을 언제 아나

v2를 배포한 시점을 0으로 두고, 탭이 v2의 존재를 안 시각을 쟀다. 탭은 6초까지 가만히 있다가 한 번 다른 화면으로 이동한다.

| 방법 | 알게 된 시각 | 추가 비용 | 메모 |
| --- | --- | --- | --- |
| 응답 헤더(`x-latest-build`) | 다음 요청 때(6.31초) | 없음 | 요청이 있어야 안다 |
| 5초 폴링(`/version.json`) | 4.18초 | 탭마다 분당 12회 | 숨겨진 탭은 브라우저가 타이머를 늦춘다 |
| 탭 복귀(`visibilitychange`) | 돌아온 직후, +9ms | 돌아올 때마다 1회 | 오래 머문 탭도 잡는다 |
| SSE | 0.003초 | 탭마다 연결 1개 | 실시간 알림 연결이 이미 있다면 거기에 싣는다 |
| Service Worker | 다른 화면으로 이동했는데도 몰랐다. `registration.update()`를 부른 8.02초에야 앎 | `sw.js` 요청 | 브라우저는 문서를 새로 열 때만 워커를 확인한다 |
| BroadcastChannel | 다른 탭이 안 지 1ms 뒤 | 없음 | 한 탭만 확인해도 모든 탭이 안다 |

Service Worker는 "브라우저가 알아서 확인해 주는" 방법처럼 보였지만, 같은 문서 안에서 화면만 바꾸는 SPA에서는 이동만으로 확인이 일어나지 않았다.

</section>

### 탭이 숨겨졌을 때가 가장 자연스러웠다

  <img src="/notes/stale-tab-after-deploy/browser-hidden.png" alt="실제 Chrome 창 네 장. 1. 회색 헤더의 v1 글쓰기 화면에서 결재 의견을 쓰는 중이다. 2. v2 배포 직후에도 화면은 그대로 v1이다. 3. 다른 탭을 보는 동안 숨은 탭의 제목이 글쓰기 · v2로 바뀌어 있다. 4. 돌아오면 초록 헤더의 v2 화면이고 작성 중이던 글이 그대로 있다." width="1200" height="697" />
  <figcaption>다른 탭을 보는 사이 숨은 탭이 v2로 새로고침됐다(3번의 탭 제목). 돌아왔을 때 작성 중인 글도 남아 있었다.</figcaption>
</figure>

- 사용자가 보고 있지 않을 때 새로고침이 끝나서, 돌아온 순간 기다림 없이 v2였다.
- 조건이 두 가지 있다. 작성 중인 글은 `sessionStorage`에 저장해 두어야 하고, 저장하지 않은 글이 있으면 새로고침을 미뤄야 한다. 실험에서도 저장하지 않은 경우는 v1로 남겨 글을 지켰다.
- 스크롤 위치는 브라우저에 맡기면 잃었다. 새로고침 뒤 목록 데이터가 늦게 와서, 브라우저가 위치를 되돌리려던 순간에는 페이지가 짧았기 때문이다. 앱이 위치를 저장했다가 목록을 그린 뒤 되돌려야 했다.

### 새로고침의 빈 화면은 미리 렌더링으로 없앴다

<figure className="note-figure">
  <img src="/notes/stale-tab-after-deploy/browser-swap.png" alt="실제 Chrome 창. 위 줄은 일반 새로고침으로 0초에는 회색 헤더 v1, 0.25초에는 초록 헤더 v2인데 본문이 비어 있고, 0.55초에 상품 17 근처 목록이 보인다. 아래 줄은 미리 렌더링 후 교체로 0초부터 초록 헤더 v2와 같은 위치의 목록이 보인다." width="1400" height="731" />
  <figcaption>교체 신호를 보낸 시점이 0. 새로고침은 0.25초에 본문이 빈 v2를 보여줬고, 미리 렌더링한 v2는 0초 칸부터 완성된 화면이었다.</figcaption>
</figure>

- 새 버전을 알면 `<script type="speculationrules">`로 지금 주소의 v2(`?__v=v2`)를 미리 렌더링하게 했다. 교체 순간에는 `location.replace()`로 그 주소로 가고, 꺼낸 페이지가 주소의 표시를 지운다.
- 미리 렌더링한 v2는 교체 신호보다 2.2초 앞서 이미 실행됐고(`document.prerendering`), 1.9초 앞서 목록까지 그려 두었다. 꺼내는 데는 10~19ms가 걸렸다(5회, `activationStart`로 확인).
- 대가가 있다. v2를 미리 받는 만큼 서버 요청이 늘어난다. 배포 순간 모든 탭이 한꺼번에 미리 렌더링하면 서버에 몰릴 수 있어, 실제로는 무작위로 시점을 흩뜨려야 할 것이다. Chromium 계열에서만 확인했다.

### 뒤로 가기는 이전 버전을 두 가지 길로 되살렸다

v1 화면에서 다른 사이트로 갔다가, 그사이 v2를 배포하고 뒤로 가기를 눌렀다.

| 되살아난 길 | 언제 | `pageshow` | 확인하지 않으면 | `persisted`만 확인 | 기록 이동(`back_forward`)까지 확인 |
| --- | --- | --- | --- | --- | --- |
| bfcache | 페이지가 bfcache에 들어갔을 때 | `persisted: true` | v1 그대로 | 0.33초에 v2 | 0.33초에 v2 |
| HTTP 캐시의 HTML | bfcache에 못 들어갔을 때(예: `unload` 핸들러) | `persisted: false`, `type: "back_forward"` | v1 그대로 | **v1 그대로(놓침)** | 0.34초에 v2 |

두 번째 길은 예상하지 못했다. HTML 응답이 `Cache-Control: no-cache`였는데도, Chrome은 뒤로 가기에서 서버에 다시 묻지 않고 캐시에 남은 v1 HTML로 문서를 새로 열었다. 그래서 "bfcache로 돌아왔는가"만 보면 놓치고, 탐색 종류가 `back_forward`인지까지 봐야 했다.

### Navigation API 라우터의 함정 세 가지

직접 만든 라우터는 Navigation API의 `navigate` 이벤트를 가로챈다. 그런데 새 버전으로 넘어가려는 이동도 이 이벤트로 들어와, 처음에는 세 번 모두 실패했다.

1. `location.reload()`도 `navigate` 이벤트(`navigationType: "reload"`)다. 이것까지 가로채면 문서를 새로 받지 않고, v1 코드로 화면만 다시 그린다. 서버에는 문서 요청 없이 데이터 요청만 왔다.
2. 미리 렌더링한 주소로 가는 `location.replace()`도 가로채면, v2를 꺼내지 않고 v1이 그 주소를 다시 그린다.
3. 꺼낸 v2가 주소의 표시를 지우려고 부른 `history.replaceState()`도 `navigate` 이벤트를 발생시켜, 같은 화면을 한 번 더 그렸다.

새 문서로 넘어가야 하는 이동은 라우터가 가로채지 않게 해야 한다. 반대로 이 성질을 이용하면 "다음 이동 때 전체 이동"은 간단하다. 탭이 이전 버전이라는 것을 알면, 다음 링크 이동을 가로채지 않으면 된다. 브라우저가 알아서 새 문서를 받는다.

같은 포트에서 v1 서버를 v2로 교체하고, v1 탭에서 각 동작을 해 봤다.

- Server Action은 코드가 완전히 같아도 빌드마다 ID가 달라졌다. 같은 암호화 키로 두 번 빌드하자, 본문이 다른 액션까지 ID가 같아졌다. ID는 키·파일·이름으로 정해지는 것으로 보인다. 다만 키를 고정하면 이전 탭이 새 서버의 새 구현을 부르게 되므로, 액션의 인자와 반환 형식은 하위 호환으로 바꿔야 한다.
- 이동 중에 생긴 오류를 전체 이동으로 바꾸는 실험 설정(`experimental.appNavFailHandling`)도 코드에 있다. 이동 중이 아닐 때의 오류는 대상이 아니라서, 모달 같은 경우는 이전 파일 보존이 더 확실했다. 이 설정은 측정하지 않았다.

## 실험 후, 내 판단은 어떻게 바뀌었나?

| 처음 세운 가설 | 관찰 |
| --- | --- |
| 이전 파일만 남기면 지연 로딩 오류는 사라진다. 서버 쪽 약속이 바뀌면 여전히 깨진다 | 맞았다. Server Action은 코드가 같아도 깨졌고, 키를 고정해야 했다 |
| 버전 고정은 요청 헤더 하나로 만들 수 있다 | 맞았다. 대가는 두 버전의 서버 코드를 함께 돌리는 것 |
| 응답 헤더와 탭 복귀 확인이면 충분하다 | 맞았다. Service Worker는 SPA에서 기대만큼 스스로 확인하지 않았다 |
| 다음 이동, 숨겨졌을 때, 뒤로 가기가 자연스러운 순간이다 | 맞았다. 뒤로 가기는 bfcache 말고 HTTP 캐시로도 이전 버전이 돌아와, 확인 조건을 넓혀야 했다 |
| 미리 렌더링으로 빈 화면을 없앨 수 있다 | Chrome에서 맞았다(0.63초 → 0.015초) |

### 잦은 배포에서 쓸 조합

1. **배포가 열린 탭을 깨지 않게 한다.** 해시가 붙은 정적 파일은 지우지 않고 쌓는다(가장 오래 열려 있는 세션보다 길게). Server Action 키를 고정한다. API는 하위 호환으로만 바꾸고, 그럴 수 없을 때만 버전 고정을 쓴다.
2. **새 버전은 싸게 알아챈다.** 모든 응답에 빌드 헤더를 싣고, 탭으로 돌아올 때 한 번 확인하고, 알게 된 것은 BroadcastChannel로 다른 탭에 나눈다. 폴링이나 SSE는 실시간 공지가 꼭 필요할 때만, 그것도 이미 있는 실시간 연결에 싣는다.
3. **넘어가는 순간을 고른다.** 다음 이동 때 전체 이동, 탭이 숨겨졌을 때(작성 중인 글은 저장해 두고), 뒤로 가기로 돌아왔을 때(`back_forward` 포함). Chrome에서는 교체를 미리 렌더링으로 감출 수 있다.
4. **즉시 넘기는 것은 호환이 깨지는 배포에만 쓴다.** 모바일 앱의 "최소 지원 버전"처럼, 서버가 "이 빌드보다 오래된 탭은 지금 바꿔야 한다"는 신호를 따로 보내는 방식이 맞다고 본다.
5. **지금 쓰던 ChunkLoadError 안내 UI는 마지막 안전망으로 남긴다.** 감지는 메시지가 아니라 `error.name`으로 하고, 브라우저 기본 모듈의 `TypeError`도 함께 본다.

결국 ChunkLoadError는 "오류를 잘 보여주는 문제"가 아니라 "배포가 열린 탭을 깨뜨리는 문제"였다. 깨뜨리지 않으면 넘어갈 때를 고를 여유가 생긴다.

### 아직 확인하지 못한 것

- Safari·Firefox. 미리 렌더링은 Chromium 계열에서만 확인했고, 다른 동작도 Chrome에서만 쟀다.
- 배포 순간 많은 탭이 한꺼번에 v2를 미리 렌더링할 때의 서버 부하
- 오래 숨겨진 탭. Chrome은 5분 넘게 숨겨진 탭에서 이어 실행되는 타이머를 조건에 따라 1분에 한 번으로 늦추고, 메모리가 부족하면 탭을 버렸다가 다시 열 때 새로 불러온다. 버려졌다 돌아오는 탭은 저절로 최신이 되지만, 측정하지는 않았다.
- 실제 사용자 데이터. 이 실험은 같은 컴퓨터 안의 측정이다.
