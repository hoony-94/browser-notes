## 먼저 결과부터

페이지 중간으로 바로 들어오는 경우, 히어로 이미지에 높은 우선순위를 주면 도착한 화면의 이미지가 늦게 보일 수 있었다. 이번 실험에서는 그 영향보다, 해시 위치로 이동하기 전에 상단 이미지가 먼저 요청되는 동작의 영향이 더 컸다.

비교한 방법 중에서는 도착 화면의 이미지를 미리 요청하고 첫 렌더를 문서 끝까지 미룬 조합이 도착 화면을 가장 빨리 완성했다. 하지만 사용자가 빈 화면을 보는 시간이 길어졌고, 보이지 않는 상단 이미지도 여전히 내려받았다. 사용자 경험까지 좋아지는지는 아직 확인하지 못했으므로, 실제 서비스에 적용하려면 추가 검증이 필요하다고 본다.

## 처음 보는 화면이 페이지 중간이라면, 상단 이미지의 preload는 여전히 유효할까?

- 히어로 이미지나 페이지 상단의 중요 이미지를 preload하고 있다면, 사용자가 처음 보는 화면이 페이지 중간일 때도 이 우선순위는 유효할까?
- 상단 이미지의 preload와 실제로 보이는 이미지의 요청이 겹친다면, 어느 쪽을 우선해야 할까?
- 링크로 페이지 중간에 바로 도착한다면, 도착한 화면의 이미지를 먼저 받을 수 있을까?

### 이 질문을 시작한 계기

보통 히어로나 첫 화면 이미지는 preload하거나, `fetchpriority="high"`로 요청 우선순위를 높여 둔다. 그런데 목차 링크, 공유받은 링크, 검색 결과처럼 페이지 중간으로 바로 들어오면 처음 보는 화면은 히어로가 아니다. 그때도 이 우선순위가 맞는지, 아니면 도착한 화면의 이미지를 먼저 받아 빨리 보여줄 수 있는지 궁금했다.

찾아보니 이 경우를 위한 공식 기능은 없었다. preload와 `fetchpriority`는 화면 위치를 모르는 고정된 힌트이고, URL의 해시(`#section-5`)는 서버로 전송되지 않는다. `loading="lazy"`와 Chrome이 화면 안 이미지의 우선순위를 올리는 동작은 실제 화면을 보지만, 보이지 않는 이미지를 미루는 쪽이지 보이는 이미지를 앞당기는 기능은 아니다. [web.dev · Fetch Priority ↗](https://web.dev/articles/fetch-priority)

### 처음 세운 가설

- 중간으로 들어오면 히어로 힌트는 화면에 보이지 않는 이미지에 대역폭을 먼저 줘서 도착 화면을 늦출 것이다. 다만 손해는 히어로 한 장 크기 정도로 작을 것 같다.
- 브라우저는 해시를 처음부터 알고 있으니, 도착 위치로 이동하고 나면 그 화면의 이미지를 금방 High로 올릴 것이다.
- 서버는 해시를 모르니, 도착 화면 이미지를 먼저 받게 하려면 브라우저 쪽(`<head>`의 스크립트)에서 판단해야 할 것이다.

## 쇼핑몰 같은 긴 페이지를 `#section-5`로 연다

상품 이미지가 많은 목록 페이지를 흉내 냈다. 맨 위에 히어로가 있고, 섹션 10개에 상품이 6개씩 있다. 이 페이지를 `#section-5`로 바로 열고, 도착한 화면의 이미지가 모두 보이기까지 걸린 시간을 비교했다.

| 항목 | 조건 |
| --- | --- |
| 브라우저 | Chrome 155. |
| 화면 | 390 × 844 (모바일) |
| 페이지 | 히어로 200 KB 1장 + 상품 40 KB 60장. 상품 이미지는 `loading="lazy"`, 모든 이미지에 `width`·`height`를 지정해 높이 변화는 없앰 |
| 서버 | Node.js 22.14.0 `http2`(TLS). 연결 하나의 내려받기 대역폭을 서버가 흉내 냄 |
| 네트워크 | 느린 망 1.6 Mbps + 응답마다 150 ms 지연, 빠른 망 9 Mbps + 40 ms, 제한 없음(대역폭 제한 없이 같은 컴퓨터 안에서 바로 전송) |
| 캐시·연결 | 측정마다 새 브라우저 컨텍스트(빈 캐시, 새 연결) |
| 반복 | 조건마다 10회, 중앙값 |

이미지는 크기만 맞춘 SVG라 끝까지 받아야 그려진다. 실제 JPEG·WebP는 받는 도중 일부가 먼저 보일 수 있다.

### 서버가 우선순위를 따르느냐도 조건으로 넣었다

HTTP/2에서는 연결 하나로 여러 응답이 동시에 오고, 대역폭이 좁으면 어떤 응답의 데이터를 먼저 보낼지는 서버가 정한다. 브라우저는 요청마다 `priority` 헤더(RFC 9218)로 우선순위를 알려주고, 도중에 바꾸면 PRIORITY 프레임으로 다시 알린다. 하지만 이것은 힌트일 뿐 서버가 따를 의무는 없다. 실제로 서버·CDN의 우선순위 처리가 제대로 동작하지 않는다는 지적도 많았다. [RFC 9218 ↗](https://www.rfc-editor.org/rfc/rfc9218.html) · [Patrick Meenan · Velocity 2019 ↗](https://conferences.oreilly.com/velocity/vl-ca/public/schedule/detail/74562)

그래서 서버가 대역폭을 나누는 방식을 두 가지로 나눴다. 하나는 우선순위를 따르고, 다른 하나는 우선순위를 무시하도록 했다. 실제 서비스는 그 사이 어딘가에 있을 것이다.

| 서버 | 대역폭을 나누는 방식 |
| --- | --- |
| 우선순위를 따르는 서버 | 브라우저가 알려준 우선순위가 높은 응답부터 보낸다. 도중에 바뀐 우선순위도 반영한다 |
| 우선순위를 무시하는 서버 | 진행 중인 응답이 대역폭을 똑같이 나눈다 |

DevTools의 네트워크 스로틀링은 브라우저 안에서 요청마다 늦추는 방식이라, 서버가 우선순위를 따르는지에 따른 차이를 재현하기 어렵다고 보고 쓰지 않았다.

### 무엇을 재나

**도착 화면 완성**은 도착 화면에 보이는 이미지 8장(섹션 5의 6장과 섹션 6 첫 줄 2장)이 모두 그려지고, 사용자가 실제로 그 화면을 보고 있는 시각이다. 이미지가 먼저 다 와도 아직 맨 위를 보고 있거나 첫 화면 전이면 보이지 않으므로, 세 시각 중 가장 늦은 시각으로 정했다.

## 실험 1 · 상단 힌트는 도착 화면을 늦출까?

먼저 히어로 힌트만 바꿨다. 이 실험의 HTML은 15 KB다.

| 조건 | 히어로 | 도착 섹션(섹션 5) 상품 이미지 |
| --- | --- | --- |
| A | 힌트 없음 | `loading="lazy"` |
| B | `<img fetchpriority="high">` | lazy |
| P | `<link rel="preload" as="image" fetchpriority="high">` | lazy |
| C | 힌트 없음 | `loading="eager" fetchpriority="high"` (서버가 위치를 안다고 가정) |
| D | `fetchpriority="high"` | eager + high |

- **우선순위를 따르는 서버**: 히어로 이미지의 우선순위를 높이면(B·P) 도착 화면이 2.39초에서 2.78초로 0.39초 늦어졌다. 도착 섹션 이미지의 우선순위를 높인 C는 첫 이미지가 1.98초로 빨라졌지만, 화면 아래에 걸친 섹션 6 이미지 2장이 Low로 남아 완성은 A와 같았다.
- **우선순위를 무시하는 서버**: 모든 조건이 약 8.96초였다. 힌트의 효과가 없었다.
- **맨 위로 들어오면**: 우선순위를 따르는 서버에서 B의 히어로는 4.15초에서 1.75초로 빨라졌다. 힌트가 원래 목적대로는 동작했다. 우선순위를 무시하는 서버에서는 둘 다 4.15초였다.
- **빠른 망과 제한 없음**: 9 Mbps에서는 차이가 0.1초 안팎이었고, 대역폭 제한이 없을 때는 차이가 없었다. 이미지끼리 경쟁할 일이 없으면 무엇을 먼저 받든 같다.

### 예상과 달랐던 것

DevTools와 요청 기록을 보니, 히어로 힌트의 손해보다 브라우저가 도착 위치를 반영하는 방식이 결과를 더 크게 좌우했다.

**① 해시 위치로 이동하기 전에, 맨 위 화면이 한 번 처리됐다.** 느린 망에서는 HTML이 다 오기 전인 0.2초쯤 맨 위 화면이 먼저 그려지고, 0.24초에 섹션 5로 이동했다. 그 사이 브라우저가 페이지 상단을 기준으로 lazy 이미지를 불러올지 판단하면서 섹션 1~3의 이미지 14장(560 KB)이 요청됐다. 화면에 보인 이미지는 8장인데, 히어로까지 43장(1.88 MB)을 요청했다. 대역폭 제한이 없어 HTML이 한 번에 오는 조건에서는 이런 일이 없었다(29장).

이때 맨 위 화면에 있던 히어로와 섹션 1 이미지는 High로 올라갔고, 화면 밖으로 밀려난 뒤에도 내려가지 않았다.

**② 도착 화면 이미지는 Low로 요청됐고, 다른 이미지 하나의 다운로드가 끝난 직후에야 High로 올라갔다.** 모든 측정에서 그 차이가 2~19 ms였다. 이미지 크기를 미리 지정해 둔 페이지라, 그 전까지 레이아웃이 다시 일어나지 않아서인 것 같다.

A가 2.39초로 나쁘지 않았던 것은 ①과 ② 덕분이었다. 우선순위가 잘못 High로 올라간 섹션 1 이미지의 다운로드가 먼저 끝나면서, ②의 재계산이 0.78초로 앞당겨졌다. 그런데 브라우저가 올린 우선순위가 서버에 늘 전달되지는 않았다. 브라우저 기록에서는 히어로도 High로 바뀌었지만, 서버 기록에는 히어로 이미지의 우선순위가 High로 전달된 내역이 없었다. 섹션 1 이미지의 High가 서버에 전달되지 않은 1회는 도착 화면이 8.76초까지 늦어졌다.

**답**: 중간으로 들어오면 히어로 힌트는 유효하지 않았다. 우선순위를 따르는 서버에서는 0.39초 손해였고, 무시하는 서버에서는 효과가 없었다. 도착 섹션에만 `fetchpriority="high"`를 줘도 화면 전체는 빨라지지 않았다.

## 실험 2 · 해시를 `<head>`에서 읽으면 도착 화면을 먼저 받을 수 있을까?

서버는 해시를 모르지만 `<head>`의 인라인 스크립트는 `location.hash`를 HTML 맨 앞에서 읽을 수 있다. 실험 1의 ①과 ②를 피하려면, 우선순위를 바꾸는 것과 함께 첫 렌더 시점도 건드려야 할 것 같았다.

### 실험 전에 확인한 것: Chrome은 파싱이 끝난 뒤 이동했다

Next.js처럼 본문 뒤에 데이터(RSC payload)가 붙는 페이지를 흉내 내려고 HTML 끝에 100 KB를 붙였다(전체 115 KB). 각 섹션 바로 뒤에 파싱 시각을 남기는 작은 스크립트도 넣었다.

느린 망에서 섹션 5는 0.21초에 파싱됐지만, Chrome은 문서 파싱이 끝난(0.74초) 직후인 0.75초에야 이동했다. 그 0.5초 동안 맨 위가 보였다. HTML 명세는 파싱 도중에도 대상 요소가 생기면 이동하도록 반복해서 시도하게 되어 있고, 시도 간격만 구현에 맡긴다. [HTML · try to scroll to the fragment ↗](https://html.spec.whatwg.org/multipage/browsing-the-web.html#try-to-scroll-to-the-fragment)

그래서 대상 요소까지만 첫 렌더를 미루는 방법(E2t)과 문서 끝까지 미루는 방법(E2)을 나눠서 비교했다. 렌더를 미루는 데는 `<link rel="expect" href="#id" blocking="render">`를 썼다. 지정한 요소가 파싱될 때까지 화면에 아무것도 그리지 않게 하는 HTML 기능이다. 이 글에서는 이렇게 화면 그리기를 미뤄 두는 것을 "렌더 보류"라고 부른다. Chrome 문서는 Chrome 124부터 지원, Firefox·Safari는 미지원으로 표시하고 있다. 다만 이후에 만든 간단한 재현 예제에서는 Safari 18.6에서도 렌더 보류가 동작하는 것으로 보였다. [Chrome · Render blocking ↗](https://developer.chrome.com/docs/web-platform/view-transitions/cross-document)

### 비교한 조건

E 조건은 모두 `<head>`의 스크립트가 해시를 보고 결정한다. 해시가 없으면 히어로 preload만 넣는다. HTML에 `fetchpriority`를 직접 쓰면 스크립트보다 preload scanner가 먼저 보고 요청하므로, 히어로 `<img>`에는 쓰지 않았다.

| 조건 | 해시가 있을 때 |
| --- | --- |
| A, B, C | 실험 1과 같음 |
| E1 | 도착 화면 이미지(그 섹션 + 다음 섹션 첫 줄)를 preload + high |
| E2t | `rel="expect"`로 도착 요소(`#section-5`)가 파싱될 때까지 첫 렌더를 미룸 |
| E2 | `rel="expect"`로 문서 끝(`#page-end`)이 파싱될 때까지 첫 렌더를 미룸 |
| E3 | E1 + E2 |

```html
<script>
  const id = decodeURIComponent(location.hash.slice(1));
  const add = (attrs) => {
    const link = document.createElement("link");
    for (const name in attrs) link.setAttribute(name, attrs[name]);
    document.head.append(link);
  };
  if (!id) {
    add({ rel: "preload", as: "image", href: "/img/hero.svg", fetchpriority: "high" });
  } else {
    // 빌드할 때 만든 "섹션 id → 도착 화면 이미지" 목록 (E1)
    for (const href of landingImages[id] ?? []) {
      add({ rel: "preload", as: "image", href, fetchpriority: "high" });
    }
    // 문서 끝까지 첫 렌더를 미룬다 (E2)
    add({ rel: "expect", href: "#page-end", blocking: "render" });
  }
</script>
```

## 실험 후, 내 판단은 어떻게 바뀌었나?

처음 세운 가설 중 방향이 맞은 것은 절반 정도였다.

- **히어로 힌트가 도착 화면을 늦출 것이다**: 맞았다. 다만 손해는 0.3~0.4초였고, 서버가 우선순위를 따를 때만 생겼다. 생각보다 작은 문제였다.
- **브라우저가 도착 위치에서 금방 High로 올릴 것이다**: 틀렸다. Chrome은 파싱이 끝난 뒤에야 이동했고, 그 전에 맨 위 기준으로 lazy 이미지를 요청하고 High로 올렸다. 도착 화면 이미지는 다른 이미지가 끝날 때까지 Low였다. 히어로 힌트보다 이쪽이 훨씬 큰 문제였다.
- **브라우저 쪽에서 판단해야 할 것이다**: 맞았다. 하지만 우선순위만 바꿔서는 안 됐고, 첫 렌더 시점까지 건드려야 했다.

그리고 서버가 우선순위를 따르느냐가 생각보다 훨씬 중요했다. 무시하는 서버에서는 `fetchpriority`가 맨 위로 들어올 때조차 아무 효과가 없었다. 이 경우에는 받는 양을 줄이거나, 경쟁이 생기는 시점 자체를 미루는 것만 효과가 있었다.

그래서 제목의 질문에는 이렇게 답할 수 있을 것 같다. 페이지 중간으로 바로 들어온다면 브라우저는 도착 화면의 이미지를 먼저 받아야 한다. 그런데 지금의 Chrome은 스스로 그렇게 하지 못한다. 페이지에서 도착 화면의 이미지를 먼저 받도록 제어하려면 첫 화면이 늦어지는 점을 감수해야 한다.

### 프로덕션에 쓸 만한가?

E3는 효과가 분명했다. 하지만 바로 기본값으로 넣을 만큼은 아니라고 본다. 효과가 큰 상황은 제한적이고, 첫 화면이 늦어지는 단점도 있다.

**이득이 크려면 이 조건이 모두 맞아야 했다.**

1. **링크로 중간에 들어오는 방문이 실제로 많다.** 목차 공유, 검색 결과 딥링크, 마케팅 링크의 앵커 같은 경우다. 맨 위로 들어오면 이득이 없다.
2. **이미지가 많은 긴 페이지다.** 도착 위치 주변에 lazy 이미지가 많아야 경쟁이 생긴다.
3. **느린 네트워크를 사용하는 방문자가 많거나, 서버가 우선순위를 따르지 않는다.** 둘 중 하나만 맞아도 이득이 있었다. 9 Mbps에서는 우선순위를 따르는 서버에서 0.15초, 무시하는 서버에서 1.28초 빨라졌다. 대역폭 제한이 없으면 차이가 없었다.

여기서 헷갈리기 쉬운 점이 있다. E3끼리 비교하면 우선순위를 따르는 서버가 첫 화면(0.78초 vs 2.78초)도, 도착 화면 완성(2.36초 vs 2.78초)도 빨랐다. 무시하는 서버에서 이득이 크게 나온 것은 E3가 그 서버에서 더 빨라서가 아니라, E3를 쓰지 않은 B가 9.9초로 그만큼 나빴기 때문이다. 그래서 가장 먼저 할 일은 우선순위를 제대로 처리하는 서버·CDN을 쓰는 것이고, E3는 그다음에 고를 수단이다.

**대가는 이렇다.**

- **첫 화면이 늦어진다.** 맨 위를 보여주다 점프하는 대신, 빈 화면을 0.78초(무시하는 서버에서는 2.78초) 보여준다. 엉뚱한 화면보다 빈 화면이 낫다고 생각하지만 FCP 지표는 나빠지고, 빈 화면이 2초를 넘으면 이탈이 걱정된다.
- **스트리밍으로 화면을 먼저 보여주는 효과가 줄어든다.** 문서 끝까지 렌더를 미루면 `Suspense`로 늦게 전달되는 부분까지 기다려야 한다. Next.js에서 먼저 준비된 내용을 보내더라도 사용자는 그 내용을 바로 볼 수 없다. 이번 실험에서는 HTML 전체를 한 번에 생성했으므로, 스트리밍 페이지에서도 같은 효과가 나는지는 별도로 측정해야 한다.
- **도착 화면 이미지 목록을 관리해야 한다.** 섹션마다 첫 화면에 보일 이미지를 빌드할 때 알아야 한다. 화면 크기마다 보이는 범위가 다르고, 반응형 이미지라면 preload에도 `imagesrcset`·`imagesizes`를 똑같이 넣어야 같은 파일을 두 번 받지 않는다.
- **렌더 보류를 지원하는 브라우저가 많지 않다.** Chrome 문서에는 Chrome만 지원한다고 나와 있고, 간단한 재현 예제에서는 Safari 18.6에서도 렌더 보류가 동작하는 것으로 보였다. Firefox는 지원하지 않는다. 지원하지 않는 브라우저에서는 E1과 같아지는데, E1은 우선순위를 무시하는 서버에서 맨 위를 더 오래 보여줬다.

**그래서 실제로 쓴다면 이 순서로 할 것 같다.**

1. 먼저 해시로 들어오는 방문 비율을 본다. 적으면 아무것도 하지 않는다. 서버·CDN이 HTTP/2 우선순위를 따르는지도 함께 확인한다.
2. 많다면 히어로 preload만 조건부로 바꾼다. 해시가 있으면 넣지 않고, 없으면 스크립트로 넣는다. 맨 위 진입은 B와 같았고(1.96초 vs 2.15초), 중간 진입은 A와 같아져 0.3초를 아꼈다. 코드 몇 줄이고 잃는 것이 거의 없다.
3. E1(preload만)은 쓰지 않는다. 우선순위를 따르는 서버에서는 이득이 없었고, 무시하는 서버에서는 맨 위를 더 오래 보여줬다.
4. E3는 이미지가 많고 HTML이 한 번에 오는 목록 페이지에서만 일부 방문자에게 적용해 효과를 확인한다. 필드 데이터에서 FCP·LCP·이탈률을 함께 본다. 스트리밍하는 페이지에는 넣지 않는다.

결국 이 문제는 페이지가 우회하기보다 브라우저가 해시 위치를 먼저 반영해야 풀리는 문제라고 생각한다. E3가 하는 일(도착 화면을 먼저 받고, 도착 화면부터 그리기)은 브라우저가 해시를 처음부터 알고 있으니 스스로 할 수 있는 일이다.

### 브라우저에 바라는 것

아래는 지금 제공되는 기능이 아니라 바람이다. 앞의 두 가지는 대역폭을 제한하지 않고, HTML 전송을 중간에 2초 동안 멈췄다가 이어 보내는 간단한 서버로 다시 재현한 뒤, 직접 Chromium에 이슈로 올렸다.

| 동작 | Chrome 155 · Canary 158 | Safari 18.6 |
| --- | --- | --- |
| 대상 요소 파싱 → 해시 이동 | 6 ms → 약 2,015 ms (파싱이 끝난 직후) | 약 15 ms → 약 2,020 ms (파싱이 끝난 직후) |
| 문서 끝까지 렌더 보류 | 첫 화면은 이동한 뒤지만, 그 전에 맨 위 기준으로 한 번 계산해 맨 위 lazy 이미지 12장을 요청 | 비슷함. 이동 8 ms 전에 맨 위가 실제로 그려짐 |

- **대상 요소가 파싱되면 그 위치로 먼저 이동하기** → [내가 올린 기능 요청 577560702 ↗](https://issues.chromium.org/issues/577560702)
  - Chrome은 일부러 기다린다. 해시는 페이지가 다 파싱되고 레이아웃된 뒤에 스크롤해야 위치를 정확히 알 수 있다는 설명이 있다. [Chromium 40769234 #8 ↗](https://issues.chromium.org/issues/40769234)
  - 그래서 "대상이 파싱되면 먼저 이동하고, 나머지가 오는 동안은 위치를 유지하자"는 대안을 함께 냈다. Safari도 같은 시점에 이동한다.
- **렌더 보류가 풀린 직후 맨 위 기준으로 계산하지 않기** → [내가 올린 버그 577605419 ↗](https://issues.chromium.org/issues/577605419)
  - 화면에 표시되지 않은 상단 이미지를 요청하거나, IntersectionObserver가 실제로 화면에 표시되지 않은 히어로를 화면에 보이는 요소로 판단하는 일이 없어야 한다.
  - HTTP/1.1에서는 이 요청들이 연결 6개를 먼저 차지해, 도착 섹션 이미지가 약 0.6초 늦게 요청됐다.
- **스크롤로 화면에 들어온 이미지의 우선순위를 바로 다시 계산하기.** 다른 이미지가 끝나는 것을 기다리지 않아야 한다. 비슷한 논의가 이미 있어서([whatwg/html #5408 ↗](https://github.com/whatwg/html/issues/5408)) 따로 올리지 않았다.
- **브라우저가 바꾼 우선순위를 서버에 일관되게 전달하기.** 히어로처럼 브라우저에서는 High인데 서버는 모르는 경우가 있었다. 다만 실험 서버(Node.js) 쪽 문제일 수도 있어서, Chrome의 네트워크 로그로 확인하기 전까지는 올리지 않았다.
